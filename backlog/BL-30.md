## Why

Hooks are how `bl` connects to worktrees, Git, agents, notifications, and anything else, without `bl` knowing those tools (D18, D27, §8).

## What

The §8 hooks: `name`, `on` (any event type), `if` (an item query plus the event terms from BL-6), `phase`, `run`, `cwd`, and `timeout`.

- `before` hooks only for `item.*` mutation events. They run synchronously with the proposed event on stdin. A non-zero exit or a timeout vetoes with exit 5 and the first stderr line.
- `after` hooks run without blocking, with bounded concurrency per event. The CLI hands them to a detached `bl` runner process, so commands return at once. The process that appended the event runs them (BL-28).
- Every after hook ends in a `hook.finished` event with outcome, exit code, duration, and `result`. The result comes from the `BL_RESULT` file (one JSON object of at most 8 KiB). If that file is empty and stdout is a single JSON object of at most 8 KiB, stdout is the result. Hooks chain with `on: hook.finished` and `if: "hook:NAME outcome:ok"`.
- Placeholders in argv and `cwd`: `{id}`, `{ref}`, `{source}`, `{url}`, `{root}`, `{branch}`, `{resource}`, and `{result.KEY}`. Expanded values must have no control characters, no leading `-`, and at most 1 KiB, otherwise the outcome is `refused`. `{resource}` comes from the coordination seam (BL-32) and is unavailable without it.
- `cwd` defaults to the directory the originating command ran in, carried along the chain, or the control root for sync-originated chains.
- Depth: events from a hook carry `cause` and depth + 1. `bl` calls inside hooks inherit `BL_HOOK_DEPTH`. Hooks don't run for events deeper than 3.
- No shell, ever (D21). A minimal environment with the §8 variables and credentials removed.
- docs/automation.md documents hooks with tested examples: `notify-ready` on `item.readiness` and the §8 `agent` hook chained after the `work` action (BL-31 adds the action side).

## Acceptance criteria

- [ ] A vetoing before hook makes the command exit 5 with the first stderr line and write nothing; a timeout also vetoes
- [ ] After hooks add no measurable delay to CLI exit beyond spawning, and each produces one `hook.finished` event with outcome, exit code, duration, and result from `BL_RESULT` or JSON stdout
- [ ] A two-hook chain runs against a fake `wt` and a fake `worklease`: the second hook runs in `{result.path}` from the first hook's JSON stdout, with the item's `{branch}` and `{resource}`
- [ ] A placeholder value with a leading `-` or a control character, or a missing `{result.KEY}`, produces outcome `refused` and runs nothing; shell metacharacters pass literally
- [ ] A hook chain that loops stops at depth 3, through both `hook.finished` chaining and `bl` calls inside hooks
- [ ] A canary test proves hooks receive only the documented variables and no credential variables

## Plan

1. Reuse BL-28's event append/dispatch ownership and BL-6's event-aware predicates. Before hooks apply only to proposed item mutation events, before optimistic publication or writes; readiness and completion events are after-only. Reject invalid phase/event combinations at config validation.
2. Build one argv-only executor shared with BL-31. Expand argv and cwd with the design.md §8 placeholders, reusing BL-20 branch names and BL-32 resource identity. Validate each expanded value for controls, a leading dash and the 1 KiB limit; missing values refuse execution. Carry originating cwd through chains, with the control root only for sync-originated chains.
3. Provide the exact §8 allowlisted environment and triggering event JSON on stdin. Capture at most one 8 KiB JSON object from BL_RESULT, otherwise single-object JSON stdout; bound reads/output, refuse malformed/oversized results with a documented outcome and never publish credentials. Propagate cause and depth through both completion chains and nested bl calls.
4. After hooks execute with bounded concurrency through the detached CLI runner or TUI worker. Emit exactly one hook.finished including outcome, exit code, duration and result, then route it through ordinary subscriptions; events beyond depth 3 trigger no further hooks. Do not retry or run hooks for deduplicated events.
5. Verify veto/timeout no-write, result precedence/bounds, placeholder refusal, originating-cwd propagation, canary isolation and both recursion paths. Exercise a fake wt -> fake worklease result chain and docs/automation.md examples; run task test and task race. Release on done is built in (D20) and tested in BL-32, not a hook.
6. Finish with task ci; record each criterion's evidence with `ac ID check N --evidence`, naming the actual command and result. Keep unmet checks open, obtain the required independent verification for substantial changes, and hand off implementation delivery before making dependent work eligible. Do not push or publish without explicit authorization.
