The Beads source refuses anything but embedded Dolt and refuses `sync.remote` (`internal/source/beads/beads.go:50`, `:72`). Beads has its own multi-host model: every host runs `bd` against one shared Dolt SQL server. Supporting server mode lets several hosts use one Beads database through `bl` with no `bl serve` (BL-70).

Compared with serving Beads through BL-70, this keeps Beads' own transactions and access control, but every host needs `bd` and network access to the database, and `bl` still runs one `bd` process per refresh and write.

## Draft until decided

1. **bd version.** Does `bd` 1.3.0 (the pinned version) support server mode with the same `--json --readonly --sandbox` reads, or does this need a newer pin?
2. **Concurrent writers.** `bd update` guards only status and assignee (`--if-status`, `--if-assignee`). How do two hosts writing the same issue behave, and does the version reread still catch it? This needs a live probe like the ones in Worklease §3.
3. **Remotes.** Dolt remotes push and pull, which is the sync D9 rules out. Keep refusing them, and name server mode in the error.
4. **Cost.** Each refresh is one `bd list` over the network every 15 s per host. Measure it at 10k issues against the §11 budgets.

## Acceptance criteria

- [ ] A Beads source whose checkout uses Dolt server mode loads, reads, and writes through bd with the same version checks as embedded mode
- [ ] Two bl processes on different checkouts against one Dolt server see each other's writes on the next poll, and a stale --if-version write fails with conflict
- [ ] Dolt remotes (sync.remote) are still refused, and the error names server mode
- [ ] bl never reads, logs, or passes Dolt server credentials; they stay in bd configuration
- [ ] docs/beads.md documents server mode setup and its limits
