## Notes

Original AC2: "If not bumped, the minute change window re-reads issues blocked by an untrashed issue, so readiness updates within one window; a fake-HTTPS test covers it." Original AC3: "Request cost is bounded per untrashed issue and skipped on reconciliation." Both assumed restoring a trashed blocker would at least enter the change window the way BL-92 assumed trashing did. Live probe (/tmp/bl99-probe, Test team) disproves the shared premise: archiving, trashing, and restoring a Linear issue bump neither its own updatedAt nor any related issue's updatedAt, confirmed by polling every 10s for 90s with a watermark independent of any field the mutation could move (sanity-checked against a real title edit, which the same filter picks up within 3s). So the untrashed issue never satisfies the change window's filter:{updatedAt:{gte:$since}} and never enters Load's rows map; there is no signal in the window for mirrored code to detect. Unlike the trash direction, there is also no archivedAt-based workaround: issueUnarchive clears archivedAt back to null, leaving no timestamp to filter on. AC2/AC3 are reworded below to record this as the finding rather than silently dropped; a follow-up BL-102 tracks reaching the trash direction (which does have a live archivedAt-filter fix) via linear.go's change window.

## Summary

Live probe (Test team, /tmp/bl99-probe) found archiving, trashing, and restoring a Linear issue all bump neither the issue's own updatedAt nor any related issue's.
