## Why

Remote accounts get credentials from a helper argv or an environment variable (D17, BL-35), such as `gh auth token` or a keychain lookup that prints a personal Linear API key. That works for one person at a workstation, but it leaves token creation, scoping, rotation, and revocation to the user, and personal keys usually carry broader scopes than `bl` needs. The owner wants better authentication over time, starting with Linear and covering as many remote providers as possible.

Carried over from Worklease DRAFT-14 (archived with the queue removal, TASK-156). Worklease plan §10 set the rules this keeps: native-app OAuth only, no embedded application secret, read-only scopes first, write scopes only for enabled writes, refresh serialized per credential, no interactive login during unattended work, and tokens in an OS keychain or protected store.

## What

Opt-in, per-account OAuth login for each remote provider whose flow fits those rules, and a recorded reason for each that does not. Start after the helper seam (BL-35) and at least one remote adapter (BL-38, BL-39) exist, so OAuth extends a working credential path instead of replacing it. Candidates: GitHub, Linear, Jira Cloud, and external adapters if BL-42 allows. Native, Backlog.md, and Beads sources are local and out of scope. Split into a shared login/token-store item plus one item per provider when picked up.

Persisting refresh tokens changes D17 ("held only in memory"); update the register in the same change.
