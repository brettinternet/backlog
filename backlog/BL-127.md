A top-level status entry may list other sources' status keys under `includes`, so items from GitHub, Linear, Jira, and other sources share one board column, query term, and workflow target while keeping their stored provider key (D11). Writes to an entry resolve per item source to the one member that source accepts (D35).

## Acceptance criteria

- [x] Config: `statuses[].includes` lists member keys; a key in two entries, a member that is itself an entry, or a member whose fixed or configured category differs from its entry fails config load naming the key
  Evidence: go test ./internal/project -run TestGitHubStatusCategories: PASS incl. member category mismatch, key in two entries, member that is an entry
- [x] Board: grouping by status folds members into their entry column in workflow order; rows still show the member provider status
  Evidence: go test ./internal/query -run TestFields: PASS, included item groups under entry doing; tui/board.go folds via StatusEntry, Row.Status unchanged (verifier PASS)
- [x] Query: `status:ENTRY` matches the entry and its members; `status:MEMBER` matches only that member
  Evidence: go test ./internal/query -run TestFields: PASS, status:doing/"in progress"/linear-state match member; status:linear-state doesn't match entry item
- [x] Writes: `status=ENTRY`, board moves, quick-add, and `workflow.start`/`workflow.done` resolve to the single member the item source accepts, else refused naming the source
  Evidence: go test ./internal/engine -run TestStatusEntryResolvesPerSource: PASS, workflow.start and Store status=doing resolve to option-active; unaccepted entry refused naming source with 0 writes
- [x] design.md decision register, format.md, query.md, and tui.md describe the behavior
  Evidence: 814bd5b adds D36 to docs/design.md and updates format.md, query.md, tui.md, schemas/project-config.json (verifier PASS)
