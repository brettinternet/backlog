The first forge refresh reads every open pull request and then up to 1,000 closed and merged ones, and nothing is published until both finish. On cli/cli that was 149.5 s before any pull request showed. On pdq/houston, `bl changes TORVALD-115` sat silent for over 3 minutes, then reported the forge `unavailable` even though it had a resume cursor and 1.6 MB cached. In a workspace, LoadForges reads forges in turn, so one large repository also delays every other project's pull requests.

Open pull requests are what in-progress items link to. Closed and merged ones are mostly done items' history. Read and publish in that order.

Outcome:
- Each refresh reads every open pull request, as now, then at most 3 pages of older pull requests, continuing from the BL-194 resume cursor. A first refresh with no cache therefore returns after the open pass plus 3 pages, and later refreshes continue the backfill until it reaches changes.MaxPulls or the end.
- While older pull requests remain, the forge's status is `partial`, not `unavailable`, with a reason naming how many it has read and that it will resume, for example "reading older pull requests, 300 read, will resume". A failed page during the backfill also reports `partial` when anything is cached and the read can resume; a failed open pass stays `unavailable` with cached pull requests stale, as now.
- The backfill stops early, keeping its cursor, when a response's X-RateLimit-Remaining is below a tenth of X-RateLimit-Limit, so interactive reads and other tools sharing the token keep headroom. Open pull requests are still read.
- While any forge is `partial`, the changes tracker loads forges again 5 s after the last load finishes instead of waiting for the minute tick, and publishes after each load. With none partial, the cadence is unchanged. A rate-limited forge isn't retried before its queue's retry time.
- `.pulls.json` records the start of the last refresh that read anything, including a partial one, so Fetched is never the zero time once anything is cached.

`bl changes`, MCP `changes`, and `bl ls` with a change term run one refresh per call, as now, and report `partial` while the backfill is incomplete. They no longer wait for the whole repository.

Non-goals: progress output on stderr (a refresh is now bounded to the open pass plus 3 pages), looking up one item's pull requests directly (separate draft), concurrent forge loads, GitLab beyond what the shared RefreshPulls signature requires.
