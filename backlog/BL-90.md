Relation edits reach bl only at the hourly reconciliation because Linear does not bump the issue updatedAt. The top-level issueRelations connection may support orderBy: updatedAt (and includeArchived), which would let the minute scan page newest relations until it passes the watermark.

Verify against the live API before building: ordering and paging behavior, whether removed relations appear (archived) or vanish, workspace-wide scope and team filtering, and request/complexity cost per empty window. If removals are invisible, the scan can still add new blockers quickly while reconciliation keeps handling removals.

## Notes

Live-API findings (2026-10-26, Test team, synthetic TEST-11..17, all deleted; scripts /tmp/bl90-probe/{experiment,bump,trash}.py):

- Schema: Query.issueRelations(first,after,before,last,includeArchived,orderBy:PaginationOrderBy). No filter argument, so it is workspace-wide: team/project scoping has to be done client-side from issue{team{id} project{id}} and relatedIssue{...}. IssueRelation fields: id createdAt updatedAt archivedAt type issue relatedIssue.
- Ordering and paging: orderBy:updatedAt returns newest first. issueRelationUpdate (blocks->related) bumps the relation's updatedAt and moves it to the top. Paging with first:1 plus after:endCursor returned r2 then r1, with hasNextPage true then false.
- Removal visibility: issueRelationDelete hard-deletes. The relation disappears even with includeArchived:true, and issueRelation(id) returns "Entity not found". Trashing an endpoint issue archives the relation instead: it shows with includeArchived:true and archivedAt set, but its updatedAt is NOT bumped, so an updatedAt-ordered scan never reaches it.
- Issue updatedAt (this disproves the task's premise): for blocks and related, creating or retyping a relation bumps only relatedIssue (the target, which for blocks is the blocked issue). Deleting a relation bumps both issues. Creating a duplicate relation bumps both. Trashing a blocker does not bump the surviving issue, and the survivor's inverseRelations drop the edge.
- Cost: complexity is charged by requested page size even when the result is empty: first:1 = 6, 25 = 140, 50 = 280, 100 = 560, 250 = 1401. Personal-key quota is 2,500 requests/h and 3,000,000 complexity/h. A first:50 page every minute would cost 60 requests/h (2.4%) and 16,800 complexity/h (0.56%), plus one more page for each 50 relation changes anywhere in the workspace.

Impact on bl: the minute change window already re-reads the bumped target. Its inverseRelations update BlockedBy/Edges, so readiness is minute-level, and engine/projection.go's blockingBy reverse index also brings the "blocking" detail rows up to date. Deletes bump both sides. What stays stale until hourly reconciliation: the source issue's raw Blocks/Related after a create or retype (visible in the `blocks:` query, JSON `blocks`, source-side `related`, and a leftover "blocking" row after a blocks->related retype), and a BlockedBy pointing at a trashed blocker.

## Summary

NO-GO on an issueRelations minute scan. Readiness already updates at minute level, because Linear bumps the target issue on every relation create, retype and delete, and bumps both issues on delete. The scan would cost 1 request per empty minute window (first:50 = 280 complexity, charged even when the page is empty), i.e. 60 requests/h and 16.8k complexity/h, plus one page for each 50 workspace-wide relation changes. All it would fix is the source issue's display-only blocks/related lag. It also can't see trash-driven relation archival, because archived relations keep their old updatedAt. If source-side freshness matters later, deriving the reverse view for `blocks:` queries and `related` in the engine (as projection.go already does for "blocking") costs zero requests. docs/linear.md corrected in 7b22589.
