## Why

Some repositories can't move off Backlog.md, such as team repositories. `bl` should still be the better TUI for them (D4).

## What

`internal/source/backlogmd` reads and writes Backlog.md 1.52 files without its CLI, reusing the BL-10 mapping:

- Status, fields, sections, criteria, and comments, with minimal diffs and Backlog.md's own conventions (HTML markers, the generated `#N` criterion index, `updated_date`, quoting). Read criteria without the index and renumber it on every write, as Backlog.md does.
- Create follows Backlog.md's ID and filename rules (next number, configured zero padding, `<id> - <Title>.md`).
- `tasks/`, `completed/`, `drafts/`, and their archives, as in BL-10.
- Drafts are the `drafts/` folder, not a status: Backlog.md 1.52 rejects `status: Draft` on a task and keeps the old status when demoting. Items in `drafts/` and `archive/drafts/` show the configured draft status (D29). Setting a task's status to draft moves it to `drafts/` with the next draft ID, as `task demote` does; setting a draft's status to anything else moves it to `tasks/` with the next task ID and that status, as `draft promote` does. Unlike Backlog.md 1.52, which leaves `dependencies` naming the old ID, rewrite every reference as `bl renumber` does, and report the new ID in the outcome.
- The source's milestone catalog comes from `milestones/` and `archive/milestones/`, and its label list from `config.yml` (design.md §5). Both are read-only, and a task may reference a milestone by ID or title.
- A repository with only Backlog.md config opens read-only until the source is configured.

## Acceptance criteria

- [ ] With `BL_PROVIDER_TESTS=1`, every field `bl` reads from a fixture backlog equals Backlog.md 1.52's `task view --plain` output
- [ ] Edits and creates made by `bl` read back identically through Backlog.md 1.52, and golden diffs show minimal changes
- [ ] Capabilities are documented, and unsupported operations are not offered
- [ ] A repository with only Backlog.md config opens read-only with a prompt to configure it
- [ ] Milestone names, descriptions, and archived state, plus the configured label list, match Backlog.md 1.52's `milestone list` and `config.yml` for a fixture; a task referencing a milestone by title resolves to the same milestone

- [ ] Setting a task's status to draft and back moves it between `tasks/` and `drafts/` with new IDs as Backlog.md 1.52's `task demote` and `draft promote` do, references in other tasks follow the new ID, and Backlog.md 1.52 reads every result

- [ ] Criteria read without Backlog.md's `#N` index, and after `bl` adds or removes a criterion, Backlog.md 1.52's `task view --plain` shows sequential indexes

## Definition of done

- [ ] task ci passes on the final commit
- [ ] Every checked acceptance criterion has --evidence naming the verification command and its result
- [ ] Substantial changes had an independent verifier pass that returned PASS for every acceptance criterion
- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
- [ ] No test was deleted, skipped, or weakened
- [ ] User-visible behavior changes are reflected in README.md or docs/ in the same change

## Plan

1. Reuse BL-10's Backlog.md decoder/mapping and study Worklease v1.9.3 backlog_write.go. Add minimal-diff expected-version writes using original Backlog.md field/section conventions, not native serialization.
2. Implement capability declarations and padded/slugged creation rules with collision-safe allocation. Keep auto-detected unconfigured Backlog.md sources read-only; do not call its CLI from production code.
3. Run golden mutation/create tests and fixture fuzzing, then opt-in compatibility checks against the pinned Backlog.md version in an isolated copy. Run task test; document exact supported fields/operations and unsupported reasons.
4. Finish with task ci; record each criterion's evidence with `ac ID check N --evidence`, naming the actual command and result. Keep unmet checks open, obtain the required independent verification for substantial changes, and hand off implementation delivery before making dependent work eligible. Do not push or publish without explicit authorization.
