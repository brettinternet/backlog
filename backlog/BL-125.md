### Why

`workflow.start` and `workflow.done` are single project-wide status keys, but each provider accepts its own statuses. In this repository `workflow.done: done` suits native tasks, while the label-mode `issues` source accepts only `open`, `closed`, `unknown`, or a mapped label, so `bl done issues:N`, MCP done, and TUI `D` are rejected ("open, closed, unknown or a configured status label required"), and an agent that claimed an issue can't finish it. `start` works only because `in-progress` happens to be both a native status and a GitHub label. Linear state keys and Jira status IDs hit the same wall in any mixed project.

### Shape

Pending a design decision recorded in the design.md register (see Notes). Whatever the mechanism, `start` and `done` resolve per item source, in one engine function shared by the CLI, MCP, TUI, and `bl next --claim --start`, and claim acquisition and release stay attached to the transition (D20).

## Acceptance criteria

- [ ] The design.md register records how start and done resolve in projects mixing sources with different status vocabularies
- [ ] In this repository, bl done issues:N closes the issue, and bl next --claim --start then bl done on a ready issue round-trips on GitHub, releasing the claim
- [ ] bl done and bl start on native tasks behave as before
- [ ] An item whose source has no unambiguous start or done status is refused with a reason naming the source, before any claim is acquired
- [ ] docs/format.md and docs/github.md describe per-source workflow resolution

## Definition of done

- [ ] task ci passes on the final commit
- [ ] Every checked acceptance criterion has --evidence naming the verification command and its result
- [ ] Substantial changes had an independent verifier pass that returned PASS for every acceptance criterion
- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
- [ ] No test was deleted, skipped, or weakened
- [ ] User-visible behavior changes are reflected in README.md or docs/ in the same change

## Plan

Decision (owner, 2026-10-27): source status choices with category fallback. Record it as a new design.md register entry in the implementing commit.

- Each source reports the status keys it accepts, with categories, through one provider-neutral interface that generalizes `jiraTransitions`. GitHub derives them from config: `open`, `closed`, `unknown`, plus `statusLabels` keys or `githubProject.options`. Linear reports the bound team's states. Jira keeps per-issue discovered transitions. Native, Backlog.md, and external sources accept every configured status unless the new optional `sources[].statuses` narrows them.
- `start`/`done` resolve in one engine function: the project `workflow` key if the item's source accepts it, else that source's only accepted status in the active/done category, else refuse with `rejected` naming the source, before any claim is acquired. No per-source workflow override until an ambiguity needs one.
- Remove the `jiraTransitions` special cases in `internal/tui/edit.go` and `internal/engine/coordination.go` in favor of the shared interface. BL-126 then uses it for the TUI picker, `<`/`>`, and board moves.
- This repository: no workflow change. Optionally set `tasks` to `statuses: [draft, todo, in-progress, done]` so native tasks can't take GitHub-only statuses.
