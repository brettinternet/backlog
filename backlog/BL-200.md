Reported from pdq/houston: one item's `bl changes` shouldn't wait for the whole repository's pull requests. Once the backfill task lands, a refresh is bounded and open pull requests are complete. What's left missing while the backfill runs is an older closed or merged pull request linked to the item asked about, mostly a done item's.

Idea: while the forge is partial, `bl changes ID` and MCP `changes` also look up that item's pull requests directly. That means a GraphQL search `repo:OWNER/NAME is:pr ID` (title and body) plus `head:` for each of the item's local branch names, merged into the cache like any read.

Before making this ready, measure how long the backfill takes on cli/cli and pdq/houston after the earlier tasks. If it finishes within a few refreshes, this may not be worth the second read path. Open questions: search rate limits (30 a minute), linking rules search can't express (a branch-name prefix without a local branch, the forge's closing references), and whether the TUI should use it too.
