Read the parent epic's Freshness section first. It is the settled design. Watching CI finish should not need `R` or the browser.

## Scope

- While the shown change is an open pull request with a queued, running, or waiting check, or merge state `UNKNOWN`, re-read its detail every 15 s on the detail worker through the account queue. This bypasses the one-minute `.reviews.json` reuse only for that pull request. After 30 minutes, fall back to the per-minute cadence. Stop when nothing is pending, the change view or Changes tab closes, or the selection moves.
- An open check view re-reads its steps on the same cadence while the job runs. Its log is read once, after the job completes.
- When a shown check moves to a final state or the verdict changes, the status bar shows a notice until the next key: `✕ test (ubuntu-latest) failed`, `✓ checks passed`, `#45 ready`.
- The strip's age counts from the last successful read. A failed read keeps the last data, marked stale (D43), and the cadence continues.
- The timer only schedules worker reads. The update loop does no I/O (D14).

## Tests

- With an injected clock and the fake forge: polling starts while a check is pending and stops when checks finish or the view closes, the 30-minute fallback applies, and no request is made for a pull request that isn't shown. These catch a poller leaking after navigation and burning the account's rate limit.
- Notice text on completion and on a verdict change.

## Acceptance criteria

- [ ] Injected-clock tests prove a shown open pull request with a pending check is read every 15 s, falls back to once a minute after 30 minutes, and stops when nothing is pending or the view closes or moves
- [ ] A finished check or verdict change shows a status-bar notice until the next key
- [ ] No request is made for a pull request that is not shown, and the update loop does no I/O (D14)
- [ ] docs/tui.md and docs/changes.md describe the cadence

## Definition of done

- [ ] task ci passes on the final commit
- [ ] Every checked acceptance criterion has --evidence naming the verification command and its result
- [ ] Substantial changes had an independent verifier pass that returned PASS for every acceptance criterion
- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
- [ ] No test was deleted, skipped, or weakened
- [ ] User-visible behavior changes are reflected in README.md or docs/ in the same change
