Hooks never retry (D27), which is the right default. But after a failure the only recovery is to cause the triggering event again, which may mean a fake edit. A manual, explicit re-run would fill the gap without automatic retries.

Sketch: `bl hook rerun EVENT_ID NAME` runs trusted hook NAME against the stored event EVENT_ID as if just appended, and appends a new `hook.finished` with `cause` = EVENT_ID and the original depth + 1. It refuses when the hook's `on`/`if` no longer match the event, when the depth cap applies, or when the hook is untrusted.

Open questions before promoting:
- Dedupe: `hook.finished` versions are `(event ID, hook name, hook digest)` (internal/hooks/runner.go), so a re-run with an unchanged hook collapses into the original. It needs a re-run nonce, as no-op mutations already use.
- Should a re-run's success re-trigger hooks chained on `hook.finished` (yes, consistent with chains) and is that safe for non-idempotent chains like `worklease run`?
- Does this need a decision register entry amending D27 ("nothing retries" means nothing retries automatically)?
- Is BL-75 (failure messages) enough on its own that this is rarely needed? Revisit after BL-75 ships.
