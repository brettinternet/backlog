The Beads source refuses anything but embedded Dolt and refuses `sync.remote` (`dolt_mode` must be `embedded`, `internal/source/beads/beads.go:50`; remotes, `:69`). Beads has its own multi-host model: every host runs `bd` against one shared Dolt SQL server. Supporting server mode lets several hosts use one Beads database through `bl` with no `bl serve` (BL-70).

Compared with serving Beads through BL-70, this keeps Beads' own transactions and access control, but every host needs `bd` and network access to the database, and `bl` still runs one `bd` process per refresh and write.

## Draft until decided

1. **bd version.** Does `bd` 1.3.0 (the pinned version) support server mode with the same `--json --readonly --sandbox` reads?
   **Recommendation:** probe 1.3.0 first in a disposable checkout and record the result in docs/beads.md. If server mode needs a newer `bd`, bump the pin in a separate item before this one, because the pin applies to embedded mode too and needs its own round-trip evidence.
2. **Concurrent writers.** `bd update` guards only status and assignee (`--if-status`, `--if-assignee`). How do two hosts writing the same issue behave?
   **Recommendation:** probe it live, as in Worklease §3: two `bd` clients updating one issue on one Dolt server. Keep today's contract either way: reread and compare versions before each write, refuse a stale one, and document the remaining check-to-write race, as embedded mode already does. Don't add a `bl` lock across hosts. Exclusive work uses Worklease claims, which already contend across hosts (BL-72).
3. **Remotes.** Dolt remotes push and pull, which is the sync D9 rules out.
   **Recommendation:** keep refusing `sync.remote`. The error names server mode as the supported way to share a Beads database across hosts.
4. **Cost.** Each refresh is one `bd list` over the network every 15 s per host.
   **Recommendation:** measure at 10k issues against the §11 budgets before choosing anything. If a refresh misses them, raise the poll interval for server-mode sources rather than adding incremental reads, unless `bd` 1.3.0 has a stable filter for issues updated since a time. Background refreshes already run off the UI loop, so a slow refresh delays freshness but never input.

## Recommendation

Below the line. No current project shares a Beads database across hosts, and BL-72 already shows claims contending across hosts without it. Promote when a Beads user needs multi-host access; do decision 1's probe first, since its answer decides whether this needs a `bd` pin bump.

## Acceptance criteria

- [ ] A Beads source whose checkout uses Dolt server mode loads, reads, and writes through bd with the same version checks as embedded mode
- [ ] Two bl processes on different checkouts against one Dolt server see each other's writes on the next poll, and a stale --if-version write fails with conflict
- [ ] Dolt remotes (sync.remote) are still refused, and the error names server mode
- [ ] bl never reads, logs, or passes Dolt server credentials; they stay in bd configuration
- [ ] docs/beads.md documents server mode setup and its limits
