Creating or retyping a Linear blocks/related relation bumps only the target issue's updatedAt (BL-90). The minute window updates the target, and the "blocking" detail rows are already derived through the blockingBy reverse index (internal/engine/projection.go:204). The source issue's raw Blocks/Related fields stay stale until hourly reconciliation, though. That shows up in the `blocks:` query (internal/query/eval.go:178), in JSON `blocks`/`related`, in source-side "related" detail rows, and as a leftover "blocking" row after a blocks->related retype.

BL-90 rejected an issueRelations minute scan (60 requests/h). A zero-request fix would derive the reverse view in the engine for the `blocks:` query and related rows, as projection already does for blocking. The leftover-row case after a retype also needs the derived view to win over the stale source-side Blocks. This is low priority because readiness isn't affected.
