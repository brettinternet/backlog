Adopting a pull request item creates a real backlog item for it in one step. The PR item then disappears, because the new item's `refs` link the PR (dedup from BL-167). Read the parent epic and BL-167 first.

## Behavior

- **TUI.** On a `github-pulls` item, one key (pick a free one; check `docs/tui.md` keys and the help overlay) opens the new-item flow prefilled with the PR title, and with the PR URL in `refs`.
  - The target is resolved by D33's create-target function as if the PR source weren't selected, since `github-pulls` can't create. Quick-add tokens (`+source`, `!high`, `#label`) still work.
  - The new item uses the target's default create status, as `n` does. Don't auto-start: active transitions are claim-gated, and the person adopting may not be the one doing the work.
  - The create runs on the worker (D14) and is optimistic like other creates (D15). The PR item disappears as soon as the snapshot includes the new item.
- **One mutation.** The engine create carries `refs`, so title and refs land in one write. The PR item and the adopted item must never both be visible because a second write failed. If `model.Mutation` create can't carry refs today, extend it.
- **Parity.**
  - Add `bl new TITLE --ref URL` (repeatable) and MCP `create` `refs`, so agents can adopt in one call: `bl new "Fix flaky login test" --ref https://github.com/acme/app/pull/45`.
  - Native sources write `refs` to frontmatter as they already do for `bl set refs+=`.
  - A source whose create can't set refs refuses with `rejected` naming the field, rather than dropping it.
- **No description copy.** The PR body stays on GitHub and shows in the change view. Copying it would fork two descriptions that then drift apart.
