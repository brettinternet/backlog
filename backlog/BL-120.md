Every GitHub refresh lists every issue and project item with their relations (docs/github.md). A cold load of charmbracelet/vhs (~120 open issues) took about 11 seconds. Once a repository's issues are a source, every CLI `bl next` in an agent loop pays a full enumeration.

Adopt Linear's two-scan model (docs/linear.md "Sync"): a change window that reads issues updated since the last scan's start minus an overlap, plus project items by their own `updatedAt` (project edits don't bump the issue), and a full reconciliation at startup, hourly, and on `R`. First probe whether `blockedBy` and sub-issue edits bump `updatedAt` on either side, and record the answer in docs/github.md. Edges that don't bump it are caught only by reconciliation, as with Linear. The coverage rules in docs/remote.md still hold: an incremental scan never proves deletion.

## Acceptance criteria

- [ ] A warm load with no provider changes makes a constant number of requests regardless of issue count, asserted against the fake server
- [ ] New, edited, closed, relabelled issues and project option changes appear on the next change-window scan
- [ ] Whether blockedBy and sub-issue edits bump updatedAt is probed live and recorded; edges that do not appear by the next reconciliation
- [ ] Incremental scans never remove rows; reconciliation runs at startup, hourly, and on R
- [ ] docs/github.md sync section and docs/benchmarks.md are updated

## Definition of done

- [ ] task ci passes on the final commit
- [ ] Every checked acceptance criterion has --evidence naming the verification command and its result
- [ ] Substantial changes had an independent verifier pass that returned PASS for every acceptance criterion
- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
- [ ] No test was deleted, skipped, or weakened
- [ ] User-visible behavior changes are reflected in README.md or docs/ in the same change
