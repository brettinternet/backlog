## Why

Remote accounts get credentials from a helper argv or an environment variable (D17, BL-35), such as `gh auth token` or a keychain lookup that prints a personal Linear API key. That works for one person at a workstation, but it leaves token creation, scoping, rotation, and revocation to the user, and personal keys usually carry broader scopes than `bl` needs. The owner wants better authentication over time, starting with Linear and covering as many remote providers as possible.

Carried over from Worklease DRAFT-14 (archived with the queue removal, TASK-156). Worklease plan §10 set the rules this keeps: native-app OAuth only, no embedded application secret, read-only scopes first, write scopes only for enabled writes, refresh serialized per credential, no interactive login during unattended work, and tokens in an OS keychain or protected store.

## What

Opt-in, per-account OAuth login for each remote provider whose flow fits those rules, and a recorded reason for each that does not. Start after the helper seam (BL-35) and at least one remote adapter (BL-38, BL-39) exist, so OAuth extends a working credential path instead of replacing it. Candidates: GitHub, Linear, Jira Cloud, and external adapters if BL-42 allows. Native, Backlog.md, and Beads sources are local and out of scope. Split into a shared login/token-store item plus one item per provider when picked up.

Persisting refresh tokens changes D17 ("held only in memory"); update the register in the same change.

## Acceptance criteria

- [ ] design.md §10 records each candidate provider's OAuth evidence: public/native client support without an embedded secret (PKCE or device authorization), scopes, token lifetime and refresh, revocation, and how the authenticated principal is verified. Each unsupported provider has a stated reason.
- [ ] An explicit interactive `bl` login authenticates a configured account, opt-in per account in user config, for each provider whose flow meets the rules.
- [ ] Login requests read-only scopes first. Write scopes are requested only when the user enables writes, and source capabilities are rediscovered afterward.
- [ ] No client secret is embedded in the binary or config. Access and refresh tokens live only in the OS keychain or an owner-private store and never appear in config, argv, hook or action environments, logs, events, MCP output, or the cache; a canary token test proves it.
- [ ] After login and every refresh, the authenticated principal is verified against the configured account. A mismatch disables the account's sources with a structured diagnostic.
- [ ] Refresh is serialized per credential across concurrent TUI, CLI, and MCP processes, and a refresh race never loses a rotated refresh token.
- [ ] Expired tokens, revoked grants, insufficient scope, SSO/SAML enforcement, rate limiting, and provider downtime each produce distinct structured diagnostics in the TUI and JSON output.
- [ ] Unattended paths (MCP, `next --claim`, hooks, and actions) never start an interactive login and return an actionable authentication-required diagnostic.
- [ ] Logout revokes the grant where supported, deletes stored tokens, and purges that principal's cached rows.
- [ ] Accounts that do not opt in keep using credential helpers and environment variables unchanged.
- [ ] Fake-authorization-server tests cover login, refresh rotation and concurrent refresh, revocation, scope denial, principal mismatch, unattended refusal, and secret-leak checks.
- [ ] design.md (D17, §10) and the user guide describe the supported providers, flows, scopes, and token storage.
