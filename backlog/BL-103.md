## Why

Agents open worktrees, branches, and PRs for items, and the item never shows any of it. To review an agent's work today you leave `bl` for `gh`, lazygit, or a browser, then find the change again by branch name. Linear and Jira each attach PRs, branches, and commits to issues. `bl` should show them on the item, so the change sits next to its criteria, evidence, and notes in the TUI.

Phase 1 is read-only: find each item's changes and view their diffs in the TUI. Phase 2 posts comments and reviews. Phase 3 renders guided tours of a change that an external agent writes.

## Shape

**In `bl`, not a plugin or a separate CLI.** The value is moving between an item and its change in one keystroke, and that needs `bl`'s accounts, OAuth, HTTP queues, trust, cache, and D14 workers. A separate CLI would duplicate all of that and couldn't open from the list. A plugin system needs a second consumer first (D18), and a diff view has to meet the §11 frame budgets in-process. Keep a seam: a new `internal/changes` package that sits beside `internal/source` and doesn't extend it, so an external forge adapter on the BL-42 framing can be added later without reshaping anything.

**Model.** A *change* is one line of work, shown at its furthest stage:

| Stage | Seen through | Shows |
| --- | --- | --- |
| worktree | Linked worktree on a matching branch (read from `.git`, D5) | Path, dirty file count |
| branch | Local or already-fetched remote ref | Ahead/behind the default branch |
| pr | GitHub PR or GitLab MR, provider API | State (draft/open/merged/closed), checks, review decision, +/− |
| landed | Commits reachable from the default branch: a merge, squash, or trailer commit | SHA, subject, date |

A worktree, branch, PR, and merge that share a head branch or SHA collapse into one change, so one row tracks the work from worktree to merged.

**Links.** Links are derived and kept only in the cache, never written to item files, so they don't churn files or cause merge conflicts (D22, D28). Native format v1 stays as it is.

- Explicit: a PR, MR, or commit URL in `refs`. This needs no format change.
- Branch: the name starts with the item's `{branch}` ID prefix (`bl-12` then `-` or the end). Every branch `bl` and `wt` create already does.
- PR/MR: the head branch matches, or the title contains the ID as a whole word, or the body has `Closes|Fixes|Resolves|Refs BL-12`. Other mentions in a body don't link.
- Commit: a `Refs: BL-12` trailer, or a merge subject that names a matching branch (`Merge branch 'bl-82-dod-checks'`, which is how this repository lands work). Fast-forward and squash merges keep the link only through the trailer or the PR's merge SHA, so `bl instructions workflow` tells agents to add the trailer.
- A remote source uses the provider's own links first: GitHub `closingIssuesReferences` and cross-references, and Linear attachments. Jira's development panel API isn't public, so Jira gets derived links only.

**Forges** are configured apart from task sources, because a Linear or native backlog still reviews on GitHub:

```yaml
changes:
  git: true                                                   # local refs, worktrees, landed commits
  forges: [{type: github, repo: acme/app, account: personal}] # network-backed: needs bl trust (D16)
```

The GitHub forge defaults from an `origin` on github.com when an account for that host exists. GitHub reuses the account, OAuth, and the serial host queue. The read App needs Pull requests: read, and phase 2's write App needs Pull requests: write. GitLab comes second, through the same interface.

**Git safety.** `bl` never fetches (D9). PR diffs come from the provider API, never `refs/pull/*`. Local diffs run `git` on a worker, never per row (§11 hazard 11). `git` runs with `--no-ext-diff --no-textconv -c core.fsmonitor=false` and the D21 minimal environment, because repository config can otherwise run programs. Reading `.git` refs and worktrees spawns nothing.

**TUI.**

- A Changes detail tab after Relations, one row per change: stage glyph, `#45` or the branch, title, `+120 −30`, checks `✓ ✕ ●`, review state, and age. `enter` opens the change.
- The change view replaces the detail pane, and `backspace` returns to the item as Relations does. Its tabs are Overview (description, checks, reviewers), Files (a tree with +/−), Diff, Commits, and Conversation. The diff is unified below 120 columns and split at 120 or wider, highlighted with chroma, which Glamour already depends on, with word-level intra-line changes. `[`/`]` jump files, `[c`/`]c` jump hunks, and `/` searches, as in detail.
- Rendering is async and cached by head SHA, file, width, and theme (D14). Large files render on demand, with the 32/128 KiB caps and `m`.
- A `changes` list column shows the furthest stage of the item's most advanced change: `⇡#45 ✓`.
- Query terms (query.md): `has:change`, `change:open|merged|closed|draft`, `checks:failing|pending|passing`, `review:requested|approved|changes`. These open views such as "active items with failing checks" and "done items with nothing landed".
- `yp` copies the change URL. `O` in the change view opens it. Shipped action examples hand off to `gh pr checkout`, lazygit, or `nvim +DiffviewOpen`.

**Agents.** `bl changes ID [--json]` lists linked changes with stage, state, checks, and URL. MCP adds a `changes` tool with the same data shape. An agent can then see whether its own PR is green without calling `gh`. Diff text stays out of JSON in phase 1, because agents already have `git diff`.

## Phases (child items once decided)

1. Register change, `internal/changes` model, and local git links (worktree, branch, and landed stages) with the Changes tab and the list column.
2. GitHub forge: PR links, checks, reviews, files, and patches through the account queue, plus the read App permission.
3. Diff view: files, unified and split layouts, highlighting, and hunk navigation, within the §11 frame budgets.
4. Query terms, `bl changes`, and MCP.
5. GitLab MR forge.
6. Writes: PR comments, line review comments, and approve or request changes. A pending review is drafted in XDG state and submitted in one non-retried call, with D15 conflict and unknown-outcome rules. Capability-gated per forge (D10).
7. Guided tours (below).

## Guided tours

`bl` is not an agent runtime (§2), so it renders tours and never generates them. An action or hook runs an agent that writes a tour file, then returns its path through `BL_RESULT`. The tour is too large for the 8 KiB result itself. Use the CodeTour `.tour` JSON format: steps with `file`, `line`, and a Markdown `description`. Add a pinned head SHA and an optional criterion index per step, so a tour can say "AC 2 is met here", which links the review back to the item's criteria and evidence. Tours live in XDG state per change. The tour goes stale when the head moves and shows as stale rather than drifting onto the wrong lines. In the change view, `]t`/`[t` step through the tour with each step's narrative pinned above its hunk. Phase 2 can post a tour as a PR comment so it's shared.

## Draft until decided

1. **Register.** §2 has no change or review scope.
   **Recommendation:** add the next free decision ID, D#: "Items show linked changes (worktrees, branches, PRs/MRs, landed commits). Links are derived into the cache, plus explicit `refs` URLs, and never written to item files. Forges are configured separately from sources and reuse accounts, trust, and queues. `bl` never fetches, merges, rebases, or manages branches or CI. Reviews are capability-gated writes. Tours are rendered from external files, never generated." Add to §2 non-goals: "Merging, branch management, and CI administration (D#)."
2. **Commit trailer key.** `Refs:` is common, but other tools also use it.
   **Recommendation:** match `Refs:` and `Task:`, and have instructions write `Refs: BL-12`.
3. **Remote-source PR links.** When a GitHub Issues source is also the forge, its issue sync could carry the PR links, or the forge could fetch them on its own.
   **Recommendation:** the forge fetches them on its own, from its own incremental PR list (`updated` cursor, ETags). The issue sync and its quota stay unchanged, and every source gets links the same way.
4. **Diff engine.** Shell out to `git`, use go-git, or use only the provider's patches?
   **Recommendation:** use `git` on a worker for local stages and the provider's patches for PRs. go-git is slow on large diffs and adds a large dependency for no current need.

## Acceptance criteria

- [ ] design.md records the changes decision and the §2 change, and child items exist for each phase with their own criteria
- [ ] An item whose branch is checked out in a linked worktree shows one change from worktree to landed, which collapses once the branch merges, with no network access
- [ ] A GitHub PR linked by head branch, title, or closing keyword appears with state, checks, and review decision, and its diff opens in the TUI within the §11 navigation budget
- [ ] A change whose links are ambiguous or out of date shows as unknown or stale, never as merged or passing
- [ ] No git, network, or diff rendering runs on the update loop (D14), and git never fetches or runs external diff, textconv, or fsmonitor programs
- [ ] docs/tui.md, docs/query.md, docs/cli.md, and a new docs/changes.md specify the feature

## Definition of done

- [ ] task ci passes on the final commit
- [ ] Every checked acceptance criterion has --evidence naming the verification command and its result
- [ ] Substantial changes had an independent verifier pass that returned PASS for every acceptance criterion
- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
- [ ] No test was deleted, skipped, or weakened
- [ ] User-visible behavior changes are reflected in README.md or docs/ in the same change
