## Why

Jira's History and Linear's Activity show how an item got to where it is. `bl` already records most of the ingredients (events, claims, comments, the Git history of item files) but shows none of them together. The timeline is also where BL-103's code changes and BL-140's provider activity land.

## Shape

**Model.** An `internal/history` package composes one time-ordered list of entries per item. Each entry is `{id, time, kind, actor, session?, group?, summary, detail?, provider}`, built from independent providers.

- `id` is stable and unique within its provider (event ULID, claim ID, commit SHA, comment index plus timestamp, or a provider event ID). It's the key for deduplication and for a `--cursor` and MCP `cursor` when paging, the same as `bl events`.
- `group` makes entries nest under a span: a header entry with a start, an optional end, and a state, for example `session:ID` or `change:ID`. Sessions are the first group kind. BL-103's changes are the next (a PR from opened to checks, review, and merged) and must fit without changing the TUI or the JSON shape. Don't special-case sessions in the renderer.
- `session` on an entry links it to a session group, even when another provider produced it. A provider that knows a branch (BL-103 changes) can attach the session whose recorded `branch` matches, so History can say which agent session opened a PR. Each provider returns entries or one status (`ok`, `unavailable: REASON`, `partial`). The composition never fails because one provider failed. Providers in this item:

| Provider | Entries | Notes |
| --- | --- | --- |
| Event log (local) | created, field changes (from → to, collapsed to readable lines), status, readiness, archive, hook/action outcomes, claim acquired/released, handoffs | Uses BL-136's per-item event index in the cache. Events from this host only. |
| Claim history (Worklease) | claim epochs, including other hosts and older `bl` versions | Deduplicated against local `claim.*` events by claim ID |
| Comments | each comment | Already loaded with the item |
| Item file Git history (native, Backlog.md) | commits touching the item file: subject, author, date | Shared and durable across hosts. One `git log --follow` per item, run on a worker when History opens, with `--no-ext-diff --no-textconv -c core.fsmonitor=false` and the D21 minimal environment. Cached by item version and HEAD. |

Sessions come from BL-136's fold. Each session appears once as a group row (agent, phases, duration, handoff text, resumability from BL-138), and its individual events nest under it. Folding is what keeps a ten-session item readable.

BL-103 (changes), BL-140 (provider activity), and any later source, such as CI runs or deploys, add a provider and optionally a group kind. They need no other changes.

**TUI.** Add a History tab after Relations (tui.md "Detail"). Newest entries are at the bottom, opening scrolled to the end, with `j`/`k` moving a cursor over entries, as in Relations. `enter` expands a session row or long entry. Provider statuses that aren't `ok` show as one dim line at the top, for example `claims: unavailable (worklease not found)` or `git: not a native source`. Loading is lazy on tab open, entirely off the update loop (D14), cached by item version plus log position, and bodies follow the existing detail-loading rules (50 ms rest, keep the previous body until ready). Cap entries per render with the existing "show more" pattern (§11 hazard 9).

**CLI and MCP.** `bl history ID [--json] [--limit N] [--cursor C]` prints the same entries, with provider statuses in the JSON envelope. MCP gains a `history` tool with the same shape, so an agent can read previous sessions' handoffs before it starts. Add it to the design.md §7 tool list.

**Workspaces (D30).** History resolves through the item's own project context (events, claims, Git).

**Budgets.** Opening History must not affect navigation frame budgets. Measure a warm open on the 10k fixture with a large event log (generate ≥ 100k events) and record the result in benchmarks.md. A warm `bl history ID` should stay within the `bl show` budget.

**Docs.** Add the tab to tui.md, `bl history` to cli.md, `history` to mcp.md, and update design.md §6 (detail tabs) and D40.

## Acceptance criteria

- [ ] internal/history composes events, claim history, comments, and native item-file Git history into one ordered list; each provider reports ok, partial, or unavailable with a reason and never fails the others
- [ ] The TUI History tab after Relations groups each agent session into one row with agent, phases, handoff, and resumability, loads lazily off the update loop, and shows non-ok providers as one line each
- [ ] When BL-138 is done, History session rows resume or fork with documented keys
- [ ] bl history ID [--json] and the MCP history tool return the same entries and provider statuses
- [ ] Git history runs once per item per version on a worker with no ext-diff, textconv, or fsmonitor, in the D21 minimal environment
- [ ] A warm History open and warm bl history stay within the navigation and bl show budgets on the 10k fixture with at least 100k events, recorded in benchmarks.md

- [ ] Entries have stable IDs and optional group spans; sessions render through the generic group path, so a test provider with a new group kind renders in the TUI and JSON without renderer changes
