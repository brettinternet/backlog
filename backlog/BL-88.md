Users on Linear or Jira want to optionally scope the board, saved views, and `bl next` to the current sprint (Linear cycle, Jira sprint). bl has no sprint concept today. Linear sources are scoped only by `team`/`project`, and cycles are never fetched (internal/source/linear/linear.go:189). Jira can approximate this with `jql: '... AND sprint in openSprints()'` on the source, but that hides other work from every view, so it isn't optional per view.

The feature must be opt-in. If no query, view, or config mentions sprints, behavior, output, and performance stay exactly as they are now. A sprint becomes something to filter and group by. It doesn't change how the backlog is organized.

## Design

One neutral concept named `sprint` covers Linear cycles, Jira sprints, and later GitHub Projects v2 iterations. Docs map each provider term to it. Don't add aliases.

The important property: whether a sprint is active, future, or closed belongs to the sprint, not the issue. A sprint starting or closing doesn't bump issue `updatedAt`, so incremental issue sync can't keep that state on each item. So:

- Each item stores only the stable key of its sprint, `Item.Sprint` (the Linear cycle UUID, or the Jira site plus numeric sprint ID). Add it to the model next to `Milestone` (internal/model/model.go:59) and include it in itemjson, projection, and the item version fingerprint where remote fields are fingerprinted.
- Every sync refreshes a catalog of sprints for each source, outside the incremental issue cursor: `{key, name, state: active|future|closed, start, end, source}`. Use the same shape and flow as `Settings.Milestones` (internal/project/settings.go:68, read in internal/query/projection.go:209 and complete.go:84). This is one small request per sync, never one per item.
  - Linear: query the team's `activeCycle{id}` plus its cycles (`id number name startsAt endsAt completedAt isActive isNext isFuture isPast`), limited to recent and future ones. Add `cycle{id}` to `issueFields`. Check `listFields`/incremental: changing an issue's cycle should bump the issue's `updatedAt`, but confirm it against the live API like the relation caveat in docs/linear.md.
  - Jira: find the sprint custom field with `GET /rest/api/3/field`, matching `schema.custom == com.pyxis.greenhopper.jira:gh-sprint`. Don't hardcode `customfield_10020`. Add it to `fields` (internal/source/jira/jira.go:156). An issue can list several sprints after a carry-over. The item's sprint is its open one (active, else the earliest future one), otherwise its most recent closed one. Get catalog state from the sprint objects, then refresh the states of the sprint IDs seen through the Agile API (`GET /rest/agile/1.0/sprint/{id}`), batched and bounded. If the account can't use the Agile API, degrade to the state on the issue's sprint objects and say so in `bl doctor`.
- `current` means the source's active sprint. If a Jira project has several boards with active sprints, `current` matches any of them. `next` means the earliest future sprint. Resolve these from the catalog in the snapshot during query evaluation, never from the wall clock, so results stay deterministic and testable.

## Surface

- Query (docs/query.md): `sprint:current`, `sprint:next`, `sprint:none`, or a sprint name or key. Comma OR works like the other scalar fields. Add `sprint` to `fields`/`groupKeys` (internal/query/parse.go:50-52), to validation (eval.go:52), and to completion. If no configured source can supply sprints, `sprint:` gets a clear validation error ("no source provides sprints"); don't let it silently match nothing.
- Group and board: `group:sprint` orders columns current, next, other future sprints by start date, closed, then none.
- Views: no new view type. A user opts in with an ordinary saved view, for example `{name: Sprint, query: "sprint:current", layout: board}`. Document that example in docs/tui.md and docs/design.md §5.
- Readiness (optional, off by default): `ready.sprint: current` (or `next`) makes items outside that sprint `ineligible` with the reason `sprint`. Model it on the `excludeLabels` path from 6c9e52c (internal/engine/readiness.go) so `next --explain` reports it. This answers the request that agents not pick work outside the sprint. Unset means no change, and `bl next 'sprint:current'` still works without config.
- TUI detail and CLI text show the sprint name. JSON adds `sprint` (key) to item metadata and the catalog to `bl config show --json` or a snapshot payload, whichever already carries milestones.

## Out of scope (note as follow-ups)

- Writing the sprint (`bl set ID sprint=...`), so the field is read-only for now.
- GitHub Projects v2 iteration fields. The model must fit them (an iteration has an ID, title, startDate, and duration), but don't implement it here.
- Sprints for native, Backlog.md, and Beads.

## Constraints

- D14: no sprint resolution or catalog I/O on the Bubble Tea update loop. The catalog arrives with the snapshot.
- Jira and Linear quotas (design §11). The catalog costs one bounded request per sync per source.
- Changing a source's sprint-related config should require trust renewal only if it changes the network scope. Reading an extra field from the same endpoints doesn't.
- Add a decision register entry to docs/design.md (next free D number), and update docs/linear.md, docs/jira.md, docs/query.md, docs/tui.md, docs/format.md (if `ready.sprint` is project config), and docs/schemas.

## Tests (critical paths only)

Jira sprint selection when an issue has several sprints. `sprint:current` when the catalog state changes but the issue's `updatedAt` doesn't. That `ready.sprint` reports `ineligible` with reason `sprint`, not `blocked`. Use the existing httptest fakes in the linear and jira packages.

## Plan

Model: Item.Sprint (opaque key, display name in Names) plus a per-source catalog (Delta.Sprints) of key/name/state/dates. Roles current/next resolve from the catalog in internal/query/sprint.go. Demand-gated via Cursor.Sprints, engine.WantsSprints (ready.sprint, views, action when, query text) and Store.UseSprints (TUI filter bar), sticky in the remote cache. Linear: cycles on the first page of every scan plus cycle{id} on issues. Jira: discovered gh-sprint field, multi-sprint selection, Agile board open-sprint list. ready.sprint follows the excludeLabels path.

## Summary

Linear cycles and Jira sprints are now queryable with sprint:current|next|none|<name|key>, group:sprint orders board columns, and ready.sprint optionally limits next to a sprint. Sprint data is fetched only when used; without it requests and output are unchanged. Documented in design.md D31 and the provider/query/TUI docs.
