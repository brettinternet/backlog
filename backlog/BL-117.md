Most GitHub repositories use plain issues without Projects v2. Today every open issue is todo, so it is ready, which is unusable alongside agent loops. Let a source map issue labels to statuses, mirroring `githubProject.options`:

```yaml
sources:
  - id: issues
    type: github
    repo: acme/app
    account: personal
    statusLabels:
      ready: todo
      in-progress: active
statuses:
  - {key: open, name: Open, category: backlog}
  - {key: closed, name: Closed, category: done}
  - {key: ready, name: Ready, category: todo}
  - {key: in-progress, name: In Progress, category: active}
workflow: {start: in-progress, done: closed}
```

Reads, when `statusLabels` is set:

| Issue | Status | Category |
| --- | --- | --- |
| Closed | `closed` | done, or canceled for not planned, whatever its labels |
| Open, exactly one mapped label | the label key | the mapped category |
| Open, no mapped label | `open` | backlog (never ready) |
| Open, several mapped labels | `open` | backlog, with a finding naming the labels (fail closed) |

Label names match case-insensitively, as GitHub does. Mapped labels also stay in `labels`.

Writes: `status=LABEL` on an open issue replaces the mapped labels with that one in a single label write, keeping other labels, after the usual version preflight. `status=open` removes the mapped labels. `status=closed` closes as completed. A label status on a closed issue is refused (reopen first), so each write stays one mutation. `workflow.start` may be a mapped label, so `bl next --claim --start` works on plain issues.

Config errors: `statusLabels` together with `githubProject`, an invalid category value, or a duplicate label. Project status validation covers mapped labels.

Update docs/github.md (a "Label statuses" section before Project status), docs/guide.md config, and add a design.md decision.

## Acceptance criteria

- [ ] With statusLabels {ready: todo, in-progress: active}, an open issue labelled ready has status ready, category todo, and is ready in bl next -n 0; an unlabelled open issue is open, backlog, and never ready
- [ ] An open issue with two mapped labels is open, backlog, with a finding naming both; closed issues stay closed whatever their labels
- [ ] bl set issues:N status=in-progress replaces the mapped labels in one write and keeps other labels; status=open removes them; a label status on a closed issue is refused
- [ ] bl next --claim --start on a ready issue applies the mapped workflow.start label and claims it
- [ ] statusLabels with githubProject, invalid categories, and duplicate labels are config errors
- [ ] A BL_PROVIDER_TESTS live round trip covers label status read and write against the test repo
- [ ] docs/github.md, docs/guide.md, and a design.md decision are updated
