Found measuring the first forge refresh on cli/cli (61 open, 4,856 pull requests) on 2026-11-17: a cold `bl changes` took 149.5 s, against 3.1 s on brettinternet/noon (12). Median page times through `gh api graphql` with pullsQuery's fields:

| Page of 50, closed and merged | Time |
| --- | --- |
| Now | 4.1 s |
| Without reviewDecision and statusCheckRollup | 1.1 s |
| Same, 100 per page | 1.8 s |

Of the fields kept, body, closing references, sizes, and mergeCommit add about 0.1 s each. Each page costs 1 GraphQL point, so the cost is server time, which GitHub's secondary rate limit meters.

Decision (owner, 2026-11-17): the closed and merged pass stops reading reviewDecision and the statusCheckRollup, as BL-194 did for mergeStateStatus. A closed or merged pull request then carries no list checks or review: the Changes tab shows neither for it, and `checks:` and `review:` no longer match an item through one. The change view still reads its full detail. That pass reads 100 per page, still halving on failure down to 12.

Also reported from pdq/houston: a first refresh failed with "GitHub returned incomplete or invalid data". In a list refresh only decodeAllowing returns that, for a 2xx response whose data is null or carries a GraphQL error other than the tolerated FORBIDDEN or NOT_FOUND on closingIssuesReferences or commits. Unconfirmed, but likely a slow page's timeout reported as a GraphQL error rather than a 5xx (cli/cli answers 502, which already halves). Treat such a page like a 5xx: reread it at half size down to 12, and keep what was read if it still fails.

Scope: the GitHub forge's closed and merged pass, and GraphQL error pages in either pass.

Non-goals: the open pass's fields (a later task reads merge state only for linked pull requests), the order refreshes publish in, GitLab.

Modified files: internal/source/github/pulls.go, internal/source/github/github_test.go, docs/changes.md (Forge refresh), docs/design.md (D43), docs/query.md (change terms note).
