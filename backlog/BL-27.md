## What

`bl mcp` serves the §7 tools over stdio with `github.com/modelcontextprotocol/go-sdk`: `next`, `query`, `show`, `create`, `update`, `append`, and `criteria`. BL-31 adds `action`. BL-32 adds `claim`, `release`, `heartbeat`, and the caller context (`session`, optional `run`) on every claim-affecting call. BL-33 adds `claim`, `start`, and `session` to `next`.

- Tools share types and validation with the CLI and map errors to the same reasons. `create` takes an optional `status`, like `bl new --status`, so an agent can file a draft that is never ready (D29).
- `bl instructions` is exposed as a resource.
- docs/mcp.md shows setup for pi and Claude Code.

## Acceptance criteria

- [ ] An in-process MCP client test exercises each tool's success path and one reason-coded error
- [ ] A parity test fails when a CLI write option has no MCP equivalent
- [ ] A subprocess test runs initialize, tools/list, and tools/call over stdio
- [ ] docs/mcp.md documents every tool and its setup
- [ ] Write tools accept an optional `version`; a stale version returns reason `conflict` and writes nothing, matching `--if-version`

- [ ] `create` with `status: draft` creates a draft that `next` does not return, and an unknown status returns reason `rejected` and writes nothing, matching `bl new --status`

## Plan

1. Expose the shipped engine operations through the Go MCP SDK with shared validation/types/reason codes. Keep stdout exclusively for protocol frames. Start with foundation tools and instructions resource; BL-31/32/33 own later action/coordination options.
2. Make invocation context request-scoped from the outset. Do not capture session, explicit handle or run ownership in a process-global engine/client singleton, and never mutate process environment to select a caller. BL-32 supplies the verified ownership context; BL-33 consumes it for recovery.
3. Document the staged schemas and the invariant that a long-lived server's WORKLEASE_SESSION_ID, WORKLEASE_HANDLE or WORKLEASE_RUN_ID cannot select another caller's claim. Account configuration can remain server-configured, but invocation ownership cannot leak from the server or a preceding request.
4. Verify foundation tool success/errors and CLI parity in-process, plus initialize/list/call through subprocess stdio. Use sequential and interleaved invocation-context tests where the implementation exercises context; leave real claim/release isolation tests to BL-32. Run task test and document pi/Claude setup in docs/mcp.md.
5. Finish with task ci; record each criterion's evidence with `ac ID check N --evidence`, naming the actual command and result. Keep unmet checks open, obtain the required independent verification for substantial changes, and deliver the implementation before making dependent work eligible. Do not push or publish without explicit authorization.
