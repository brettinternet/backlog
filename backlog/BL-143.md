## Why

Someone reading Worklease directly (`worklease status`, `worklease list`, the claims TUI) sees only what Worklease stores: `sessionId`, `agentId`, and `workKey`. bl doesn't pass `--agent`, so every claim records the login user (`agent: "brett"`), which doesn't distinguish anything on one host. Agents also decorate their session: BL-136 is claimed by `claude-1deede08-…` while that session's `CLAUDE_CODE_SESSION_ID` is `1deede08-…`. So a Worklease-only reader can't tell which agent holds a claim or look the session up in Herdr or Claude Code (contact resolution is the sibling item).

Worklease stays slim and gets no new fields. bl fills the existing ones properly.

## Shape

- When BL-136 detects an agent kind (CLI detection or MCP `agent`), bl passes it to Worklease as `--agent KIND` on acquire and transfer. Without a kind, it keeps Worklease's default (login user). Pass it the same way for remote authorities. On those, the installation label already names the host, so don't encode the host into `agentId`.
- `bl instructions workflow`: use the harness session ID unchanged as the session, with no prefix or suffix, so a Worklease claim's `sessionId` alone resolves through Herdr and Claude Code. Remove any example that suggests decorated IDs.
- design.md §9: claim history `agent` is the agent kind when known.
