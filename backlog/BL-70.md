## Why

D5 gives every worktree on one host one live backlog. Agents on other hosts (devcontainers, cloud agents, CI runners, a second machine) only get their own clone, and `bl` never fetches or pushes (D9). Syncing through Git means stale reads, merge conflicts on concurrent edits (D28 resolves only `updated` and comments), and no version check across hosts, so `--if-version` and `next` can't be trusted across machines.

## Shape

`bl serve` runs one project's engine as the only writer and exposes its sources over HTTPS. Clients declare the server as a source:

```yaml
sources:
  - {id: tasks, type: bl, url: https://backlog.example.com:7443, source: tasks, account: team}
```

- **A source, not a scheduler.** Clients list, read, and apply (with expected version) over the wire, plus a change stream for `Watch`. Query, readiness, and `next` still run on the client (D12, D13). Methods and item shapes reuse external adapter protocol v1 (`list`, `read`, `apply`, `capabilities`, coverage, diagnostics). v1 is stdio-only with one request in flight and no host credentials, so this is a new HTTP binding of those methods, not a change to v1.
- **Writes keep D8 on the server.** Native writes stay atomic, minimal-diff, and version-checked under the repository write lock. `serve` holds that lock for its whole lifetime, like Worklease's hosted lock, so a second server on the same checkout is refused and `--if-version` holds across hosts.
- **Backend** is whatever the server's project config declares. Capabilities pass through unchanged, so a Beads-backed server offers only Beads' writes.
- **Claims stay out of the server** (D20, §2). Every client points Worklease at the same remote authority (`worklease serve`, selected by profile or binding). The server reports the backing project ID and source identity, so every client derives the same resource key as a local client on the server's checkout. Generic keys are already `coordination:generic:…`, which a Worklease authority admits by default. BL-72 proves this works today without a `bl` server.
- **Auth.** TLS by default. Cleartext only behind an explicit flag, as in Worklease. Clients send a bearer token resolved through the existing account methods (helper or env, D17). The server stores only token hashes, each with a read or write role. A `type: bl` source is network-backed, so a project-declared one needs `bl trust` (D16).
- **No UI-loop I/O** (D14). The client source runs on its own worker like the GitHub and Linear sources, warm-starting from the cache (D23).

## Backend tradeoffs

| | Native Markdown | Beads (`bd`) |
| --- | --- | --- |
| Writes | Everything: sections, criteria, evidence, archive | Title, status, type, priority, assignees, labels, comments |
| Version check | Content hash, atomic under the lock | Reread then write; no full compare-and-swap |
| History | Git commits, reviewable in PRs | Dolt commits in `.beads` |
| Readable without `bl` | Plain files in the repository | Needs `bd` |
| Cost per refresh or write | In-process, stat-validated cache | One `bd` process |
| Multi-host without `bl serve` | No | Dolt server mode (BL-73) |

Native should be the default and the only backend this item must verify. Beads goes through the existing source with its limits.

## Draft until decided

1. **Register.** §2 lists "a sync server or daemon" as a non-goal, so D1 needs a register change.
   **Recommendation:** add the next free decision ID, D# (D31 is taken by sprints): "One single-writer `bl serve` per project exposes its sources to remote `bl` clients. It is a source, never a claim authority, scheduler, or sync engine, and has no replicas or HA." Change the §2 non-goal to "A sync server or daemon, other than `bl serve` (D#)", and keep "A claim authority" and "A web UI" as they are. Land the register change as the first commit of this item, before any code.
2. **Git.** The server's checkout becomes the authority for `backlog/`. Who pushes, and do clients (including the primary checkout) point at the server?
   **Recommendation:** the server commits with `git.autoCommit` (one commit per applied write, as native CLI writes do today) and never pushes, keeping D9. Pushing is an operator's scheduled `git push` from that checkout, documented in docs/serve.md. Committed `backlog.yaml` keeps the `type: native` source, so a fresh clone, CI, and offline work need no server or credentials. Hosts that use the server opt in through user config `projects.<id>.sources`, which replaces the source list (D16 list-replace). A developer on such a host reads Git history but doesn't edit `backlog/` in the clone. `bl serve` refuses to start on a checkout with uncommitted changes under the source path, so it never absorbs another writer's edits.
3. **Events and hooks.** The server is the only writer, so it owns the event log (D27).
   **Recommendation:** the server appends every event once, as today. Clients read it through the change stream, and `bl events --follow` on a client shows the server's events for `type: bl` sources. In v1, no hooks run for served sources on either side: on the server they'd run with the server's privileges, and on clients each client would fire them, breaking D27's exactly-once rule. Automation runs `bl events --follow` against the server instead. Server-side hooks can come later, configured only in the server operator's user config.
4. **Offline.** What happens when the server is unreachable?
   **Recommendation:** fail closed. Reads serve cached rows marked stale, which are never ready and never satisfy a blocker (§4.3). Writes fail with `unavailable` and are never queued, because a queued write would apply against a version the client no longer knows (D15). A request whose response is lost reports `unknown-outcome`, and the client rereads before deciding anything.
5. **MCP over HTTP.** Add `bl mcp --listen`, or have every agent run a local `bl`?
   **Recommendation:** not in this item. Agents run a local `bl mcp` over stdio against a `type: bl` source, which keeps one auth surface (the source token) and §7's per-call caller context unchanged. Open a separate item when an agent runtime that can't run a local binary needs it.

## Acceptance criteria

- [ ] Clients on two hosts with a type: bl source see each other's writes within 1 s, and a write from the stale client with --if-version fails with conflict and writes nothing
- [ ] bl next --claim --start from two clients sharing one Worklease remote authority returns different items, and a client on the server's own checkout contends with them on the same resource key
- [ ] Stopping the server during a write leaves item files whole (D8); clients report unknown-outcome or unavailable, and cached rows show as stale and never ready
- [ ] Without a valid token every method is refused, a read token cannot write, and tokens never appear in logs, errors, events, or JSON output
- [ ] A Beads-backed server exposes only Beads capabilities, and unsupported writes fail before reaching bd
- [ ] The client TUI meets the §11 warm read budgets, with no network I/O on the update loop (D14)
- [ ] design.md (register and §2), docs/cli.md, and a new docs/serve.md cover the server, the source, auth, and failure behavior
