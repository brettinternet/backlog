## Why

BL-103 and its children made the change view work: Overview, Files, Diff, Commits, Conversation, review drafts, and tours. BL-166 made an unlinked pull request an item of its own. But the view still can't answer the question you open a PR to ask: **can this merge, and if not, what do I do next?**

Today:

- Checks are a flat list of name, state, and URL. No workflow grouping, no required flag, no duration, no queued, running, waiting, cancelled, or timed out. Failing checks aren't sorted first. Why a job failed means `O`, then the browser.
- Merge state isn't read: conflicts, behind base, blocked by branch protection, auto-merge, and merge queue are invisible.
- Reviewers show login and state only. No code owner or team, and an approval on an old commit looks current.
- `enter` does nothing on a check, a file, a reviewer, or a thread. Nothing in the view links to anything else.
- Review threads never appear in the Diff. Conversation bodies are plain wrapped text, so code blocks and suggestions are unreadable, and a thread has no code context.
- Threads can't be resolved, files can't be marked viewed, and reviews can't be requested.
- A `github-pulls` item opens to near-empty item tabs; its PR is two keys away (Changes tab, `enter`).
- Pending checks only refresh with the per-minute forge refresh.
- Agents still need `gh` for why CI failed and what reviewers asked: `bl changes --json` returns check names and an unresolved count, nothing more.

Goal: one place to judge, navigate, and act on a pull request, whether it belongs to a task or is its own unit of work (a D44 `github-pulls` item). Every problem shows on the first screen, and fixing it is one `enter` away.

## Principles

1. **Verdict first.** Every change view tab starts with one line that answers "can this merge?" The Overview lists each reason as an entry.
2. **Every entry goes somewhere.** `enter` on a blocker, check, step, annotation, reviewer, file, or thread opens where it's fixed or explained. `backspace` returns to the exact entry.
3. **Problems sorted first, the rest folded.** Failing then running checks, unresolved threads, unviewed files. Passing checks, resolved threads, and viewed files fold into one summary entry that `enter` expands.
4. **The forge decides, bl displays.** Merge state, requiredness, and review decision come from the forge. bl never computes mergeability. Stale never reads ready or passing (D43).
5. **Read on demand, bounded.** List refresh reads only what the list shows. PR detail is read for the change shown. Steps, annotations, and logs are read for the check shown. Everything runs on workers (D14), is redacted and stripped (D21), and is cached by head or check run.
6. **Same data for agents.** `bl changes ID --detail` and MCP `changes` `detail: true` return what the view shows.

## Layout

All mockups are at 76 content columns, the change view at 80 columns. Glyphs follow the existing set (`✓` passing, `✕` failing, `●` running); final glyphs are verified in a PTY under default, `NO_COLOR`, and high contrast.

### Verdict strip (every change view tab, under the tabs)

```
⇡ #45 → main   ✕ Blocked  1 failing · changes requested · 3 unresolved   12s
```

| Verdict | When (forge merge state first) | Color |
| --- | --- | --- |
| `Ready` | `CLEAN` or `HAS_HOOKS` | green |
| `Unstable` | `UNSTABLE`: mergeable, optional checks failing | yellow |
| `Running` | Only pending checks stand between it and ready | yellow |
| `Blocked` | `BLOCKED`, with reasons: failing or pending required checks, changes requested, review required | red |
| `Behind` | `BEHIND`: base requires an up-to-date branch | yellow |
| `Conflicts` | `DIRTY` | red |
| `Draft`, `Merged`, `Closed` | PR state | muted, magenta, muted |
| `Checking` | `UNKNOWN` while GitHub computes it | muted |

Reasons are ordered by what to fix first and truncate with `…`. The verdict and the age of the last read never truncate; the age becomes `stale` when a read fails. A stale read never shows `Ready`. Branch and worktree changes show stage, branch, `↑2 ↓1`, and dirty count instead.

### Overview

```
 Merge    ✕ Blocked                                    squash · auto-merge
   ✕ test (ubuntu-latest) failed                                 required
   ✎ ann requested changes                                             2h
   ● 3 unresolved threads
   ⚠ Conflicts with main

 Checks   ✕ 1  ● 2  ✓ 15  – 3
   CI · pull_request
     ✕ test (ubuntu-latest)   failed    4m12s  required  go test ./...
     ● lint                   running   1m03s  required
     ○ deploy-preview         waiting                    needs approval
   ✓ 15 passing · – 3 skipped                                          ▸

 Reviews  ✎ changes requested
   ann          ✎ changes requested   2h   3f2a1c9
   bob          ✓ approved            1d   outdated
   acme/core    ○ requested                code owner

 About    feat/bl-12-login → main · 3 commits · 12 files +120 −30
          opened 2d by brett · updated 12m · head 3f2a1c9
          bug, flaky · closes #33 · BL-12

 (description, Markdown)
```

- **Merge** lists one entry per reason. `enter` on a failing or pending check opens the check, on a review opens that review in Conversation, on unresolved threads opens the Diff at the first one, and on conflicts or behind opens `!` narrowed to the change's handoff actions. The heading shows merge method and auto-merge or merge queue position when set.
- **Checks** groups by workflow and event (Actions), app (other check runs), or `Statuses` (commit statuses), with one level when only one group exists. Order: failing, then running, queued, or waiting, then passing, then skipped. With more than six checks, passing and skipped fold into one summary entry; `enter` or `za` toggles it. Each row shows glyph, name, the exact state word (`queued`, `running`, `waiting`, `failed`, `timed out`, `cancelled`, `action required`, `passed`, `skipped`, `neutral`, `stale`), duration (elapsed with `…` while running), `required`, and the failed step or output title. Columns drop in this order as width shrinks: summary, required, duration. `enter` opens the check, `O` opens its URL.
- **Reviews** lists requested and submitted reviewers (users and teams), the commit each review was on, `outdated` when it isn't the head, and `code owner`. `enter` opens the reviewer's latest review in Conversation.
- **About** holds the facts the old property sheet listed, compressed: branch, base, commits, files `+/−`, author, ages, labels, assignees, milestone, closing references, linked items, and URL.
- The existing Draft block stays where it is today, between Reviews and About.

### Check (`enter` on a check, one level under Overview)

```
 ✕ test (ubuntu-latest)                                  failed · 4m12s
   CI · pull_request · required · started 14m ago

 Steps
   ✓ Set up job                                                        2s
   ✓ Run actions/setup-go@v5                                          14s
   ✕ Run go test ./...                                             3m51s
   – Post Run actions/setup-go@v5

 Annotations
   ✕ internal/auth/login_test.go:42  expected 200, got 500
   ⚠ .github/workflows/ci.yml:12  Node.js 16 actions are deprecated

 Log · Run go test ./...
   --- FAIL: TestLoginRetry (0.42s)
       login_test.go:42: expected 200, got 500
   FAIL  github.com/acme/app/internal/auth  0.512s
   Error: Process completed with exit code 1.
```

- Steps come from Checks read. `enter` on a step shows that step's log. The log opens on the failed step, or on the last step when none failed.
- `enter` on an annotation opens the Diff at its line when the file is in the change; otherwise `O` opens it.
- Log: the job log of a completed GitHub Actions job (needs Actions read, child D), cut to the step, with timestamps removed, `##[error]` and `##[warning]` lines colored, and group markers shown as headings. `]`/`[` jump between error lines, `/` searches, `m` shows more, and `yl` copies the shown step's log for pasting into an agent. Without permission, the Log line says which permission is missing and `O` opens the job.
- Other check runs show their output title, summary, and text as Markdown. Commit statuses show their description.

Order: unresolved threads in file and line order, then reviews and comments oldest first, then resolved threads folded into one entry. A thread shows the last four lines of its diff hunk. Bodies render as Markdown (Glamour, on the worker, cached), and a ```` ```suggestion ```` block renders as a small diff. `enter` on a thread opens the Diff at its line; an outdated thread says its line changed and stays put.

### List and navigation

- The `changes` cell keeps its width, but its last glyph becomes the verdict, by precedence: `⚠` conflicts, `✕` failing, `✎` changes requested, `↓` behind, `●` running, `○` review required, `✓` ready. Drafts and an unknown merge state keep today's checks glyph. This needs `mergeStateStatus` on the list read.
- `gp` from the list or detail opens the item's furthest open pull request in the change view, or its Changes tab when it has several.
- Detail on a `github-pulls` item opens in its pull request's change view. `backspace` shows the item tabs, such as History.
- With a change view open, `J`/`K` keep the same change view tab on the next item's furthest pull request, so you can triage a list of PRs without leaving the view. An item without one shows its item tabs.
- Go-to (`ctrl-p`) accepts `#45` or a pull request URL and selects the item that shows that PR: its linking item or its PR item.
- Queries: `merge:ready|unstable|blocked|behind|conflicts` and `reviewer:me|LOGIN|org/team` (requested or submitted), evaluated from the list read. Documented example views: "Needs my review" (`reviewer:me review:requested`), "Blocked" (`change:open -merge:ready`).

### Keys (new or newly meaningful)

| Key | Where | Does |
| --- | --- | --- |
| `gp` | List, detail | Open the item's pull request |
| `enter` | Merge reason, check, step, annotation, reviewer, file, thread | Open its target |
| `enter`, `za` | Folded summary, resolved inline thread | Expand or fold |
| `]u` / `[u` | Change view | Next or previous unresolved thread |
| `]` / `[` | Check log | Next or previous error line |
| `x` | Thread (Conversation, Diff) | Resolve or unresolve |
| `v` | Files, Diff | Toggle viewed |
| `yl` | Check | Copy the shown step's log |
| Palette | Change view | `Request review…`, `Re-request review`, `Ready for review` / `Convert to draft` |

Every new action is in the keymap table, help, palette, and which-key popups, and is disabled with its reason where it doesn't apply. Mouse selects entries as today; clicking a selected entry does what `enter` does.

## Freshness

While the shown pull request has a queued, running, or waiting check, or merge state `UNKNOWN`, its detail is read again every 15 s on the worker through the account queue. After 30 minutes it falls back to the per-minute cadence, and it stops when nothing is pending or the view closes. Nothing polls for a PR that isn't shown. When a shown check finishes or the verdict changes, the status bar says so (`✕ test (ubuntu-latest) failed`, `#45 ready`) until the next key.

## Writes

D43 has review writes. Add these, each one GraphQL mutation on the worker through the account queue, never retried, then reconciled by a re-read. All of them are idempotent toggles or set operations, so re-reading after an unknown outcome is safe. A refused write keeps the forge's reason visible (D15), and each is gated by D10 like `c` and `r`.

| Write | Mutation |
| --- | --- |
| Resolve or unresolve a thread (`x`) | `resolveReviewThread`, `unresolveReviewThread` |
| Mark a file viewed (`v`) | `markFileAsViewed`, `unmarkFileAsViewed` |
| Request or re-request review | `requestReviews` (`union: true`), from a picker of suggested reviewers, previous reviewers, and code-owner teams, plus typed logins |
| Ready for review or convert to draft | `markPullRequestReadyForReview`, `convertPullRequestToDraft` |

Out of scope, per the D43 non-goal: merging, enabling auto-merge, updating or rebasing the branch, re-running jobs, and closing. They stay `!` handoffs; the shipped action examples gain `gh pr merge {change.number}` and `gh pr update-branch {change.number}`. `github-pulls` items stay read-only as items (D44); pull request writes act through the change view.

## Agents

`bl changes ID --detail [--json]` and MCP `changes` with `detail: true` add, for each open pull request: `merge` (`state`, `verdict`, `reasons`, `method`, `autoMerge`, `queue`), `checkRuns` with `group`, `status`, `required`, `startedAt`, `completedAt`, and `summary`, failing runs' `steps`, `annotations`, and `log` (the failed step, capped, or `logUnavailable` with the reason), `reviewers` (`login`, `team`, `state`, `commit`, `outdated`, `codeOwner`), and `threads` (`id`, `path`, `line`, `resolved`, `outdated`, `hunk`, and `comments`). Default `bl changes` stays as cheap as today. `bl instructions workflow` names `bl changes ID --detail --json` for "why did CI fail" and "what did reviewers ask" in place of `gh`.

| Check detail (on demand, by node ID) | `steps(first:50)`, `annotations(first:50){path location annotationLevel title message}`, `summary`, `text` |

| Viewed (Files and Diff tabs) | `files(first:100){nodes{path viewerViewedState}}`, paginated |

Verify `mergeStateStatus` and `isRequired` on the live API first, including whether either still needs a preview header. Without them, the verdict comes from `mergeable` plus the check and review data, and `required` is omitted.

## Safety and budgets

- Logs: credentials never go to the redirect host, the download is capped (keep the last 1 MiB; refuse past 32 MiB and offer `O`), D21 redaction and control-sequence stripping run before display or cache, and the log is cached by check run and attempt in the state directory.
- §11: held `j` over an Overview of 300 checks, a Conversation of 200 threads, and a 10,000-line Diff with 100 inline threads meets the navigation budget. Every read and render runs on workers (D14).
- Polling stays within 4 requests a minute per shown PR, through the account's serial queue.

## Register

Record **D45, Pull request view**, in child A, and extend it in each later child. The change view answers whether a pull request can merge and why not, from the forge's merge state and reasons. Checks are grouped by workflow, with exact state, the required flag, and duration. Reviewers carry code-owner and outdated marks. Threads show inline in the Diff. Check steps, annotations, and an Actions job's failed-step log are read on demand for the check shown, bounded and redacted, never on refresh. A shown pull request with pending checks is read again every 15 s. Writes cover thread resolution, viewed files, review requests, and draft state, each one non-retried mutation reconciled by a re-read. Merging, branch updates, job re-runs, and closing stay action handoffs (the D43 non-goal).
