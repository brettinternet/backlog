Claims bl creates in Worklease are hard to recognize. The resource is an opaque `coordination:generic:<sha256>` key, and the only readable label, the work key, is `<source ID>:<item ID>` (`internal/worklease/coordinator.go` Acquire). The source ID is `tasks` in every default project, so a person looking at `worklease` cannot tell which project holds the claim.

Worklease already provides the seam: `--work-key` is documented as an opaque key "recorded with the claim for humans and history". bl should fill it with the project ID (`project.id`, derived from `origin`, portable across hosts) plus the item's display ID. Remote items whose display ID is already global (`owner/repo#12`) still get the project prefix, so the label says which project claimed it.

Do not send a checkout path: claims can live on a shared remote authority, and a path is true on one host only. A host-local project ID is the control root path, but `refuseHostLocal` already keeps those claims on the local authority, so it never leaks.

bl does not read the work key back to bind claims (`next_test.go` asserts only exact identities bind), so the change is display-only. The Worklease TUI showing the work key in its list is tracked on the Worklease side.
