A top-level status entry may list other sources' status keys under `includes`, so items from GitHub, Linear, Jira, and other sources share one board column, query term, and workflow target while keeping their stored provider key (D11). Writes to an entry resolve per item source to the one member that source accepts (D35).

## Acceptance criteria

- [ ] Config: `statuses[].includes` lists member keys; a key in two entries, a member that is itself an entry, or a member whose fixed or configured category differs from its entry fails config load naming the key
- [ ] Board: grouping by status folds members into their entry column in workflow order; rows still show the member provider status
- [ ] Query: `status:ENTRY` matches the entry and its members; `status:MEMBER` matches only that member
- [ ] Writes: `status=ENTRY`, board moves, quick-add, and `workflow.start`/`workflow.done` resolve to the single member the item source accepts, else refused naming the source
- [ ] design.md decision register, format.md, query.md, and tui.md describe the behavior

## Definition of done

- [ ] task ci passes on the final commit
- [ ] Every checked acceptance criterion has --evidence naming the verification command and its result
- [ ] Substantial changes had an independent verifier pass that returned PASS for every acceptance criterion
- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
