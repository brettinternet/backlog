Writing a tour costs agent tokens, so tours stay opt-in and the project decides. A backlog.yaml setting turns them on, chooses whether agents are nudged (the workflow suggests a tour) or required (done refuses without a current tour), and narrows which changes need one, for example only pull requests. With the setting absent, nothing mentions tours beyond the tours topic itself. Depends on the store-time step check so required tours can't be satisfied by tours that render nothing.

## Notes

With require, a tour carried forward by BL-165 whose steps are all current (none outdated) should satisfy the requirement, so agents rewrite tours only when the code a step explains changed.

Implemented in worktree bl-163-tour-setting: tours.{mode,stages} config, require gate in engine.ApplyWrite and TUI Store.runEdit, suggest tourRequest on CLI/MCP done, workflow guidance via instructions.WithTours. The require check counts only tours whose ref is the change's current head; carried-forward tours (BL-165, not yet done) need to extend engine.ToursPending to accept a tour with no outdated steps.
