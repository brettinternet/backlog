Let a task say "don't begin before DATE" so `bl next` and `is:ready` skip deferred work until then, without someone having to remove a `deferred` label on the right day.

## Prior art

- Taskwarrior: `scheduled:` keeps a task out of `+READY` until the date (closest analog: an engine-defined readiness).
- OmniFocus/Things: defer date hides the task until then.
- Jira: `Start date` field for Timeline/Plans; display only, no gating.
- Linear: no issue start date; cycles do scheduling.

## Proposal

Native `start` field plus readiness rule 5 (design.md §6): `start <= today` in the clock's time zone. Not-yet-started items are `ineligible`, matching excluded labels.

## Costs

1. Readiness becomes clock-dependent. Events come from snapshot diffs (design.md §8), and a date passing changes no data, so a time-crossing must be detected and emitted (same gap as claim expiry, design.md:465).
2. Provider mapping is thin: Linear has nothing; Jira `Start date` and a GitHub Projects date field could map via config later. Start native-only.

## Out of scope

Generic external gates (commands or URLs deciding readiness): they put I/O into readiness and break deterministic `next` and D14. Use `blocked_by` on a placeholder item or a cross-source upstream issue instead.

## Open question

Is deferral frequent enough to justify the clock dependency over a `deferred` label?

## Acceptance criteria

- [ ] Native items accept an optional `start: YYYY-MM-DD` field; invalid dates are load errors
- [ ] An item whose start date is after today is not ready, reports `ineligible` with a start-date reason in `next --explain`, and `bl next` skips it
- [ ] Queries support `start:` with the same date forms as `due:`, and `has:start`
- [ ] When an item's start date passes, the next bl process emits its ready event exactly once, so `is:ready` hooks fire without any item edit
- [ ] design.md gains a decision-register entry; format.md, query.md, and tui.md document the field
