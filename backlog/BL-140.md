## Why

For GitHub, Linear, and Jira items, most history happens in the provider: other people's edits, status changes, assignments, and cross-references. The local event log shows only what this host's `bl` observed. Each provider already exposes this activity: GitHub's issue timeline, Linear's issue history, and Jira's changelog.

## Shape

- Add a timeline provider (BL-139 model) per remote source, as a read-only, capability-gated source capability (D10). External adapters can add it later through the protocol, not in this item.
- GitHub: `GET /repos/{owner}/{repo}/issues/{n}/timeline` (or the GraphQL `timelineItems` equivalent), with project-scoped sources (D37) using the item's own repository. Map labeled/unlabeled, assigned, closed/reopened, renamed, cross-referenced, connected, and referenced events. Skip comment events, because comments come from the comments provider. Map Projects v2 status changes only if the timeline exposes them. Don't add extra project queries.
- Linear: `issue.history` (paged): state, assignee, label, priority, cycle, and parent changes.
- Jira Cloud: `GET /rest/api/3/issue/{key}/changelog` (paged).
- Load lazily, only when History opens or `bl history` runs, through the source account's serialized queue, honoring quotas (§11 hazard 7). Cache in the disposable cache by item version, with ETags where the provider supports them. Never on sync. No new credentials or App permissions: verify each endpoint works with the existing read scopes, and record that verification in the provider docs (github-verification.md and linear-verification.md style).
- Entries from the provider and local events for the same change both show, labelled by source. Don't attempt fuzzy deduplication.
- Provider text is stripped of terminal controls (D21). A failed fetch is a provider status line, never a failure of the tab.

**Docs.** Update github.md, linear.md, jira.md, and tui.md History.

## Acceptance criteria

- [ ] GitHub, Linear, and Jira sources add timeline entries from the issue timeline, issue history, and changelog, read-only and capability-gated
- [ ] Activity loads only when History opens or bl history runs, through the account queue, cached by item version, and never during sync
- [ ] Existing read scopes suffice, verified live per provider and recorded in the provider docs
- [ ] A failed or rate-limited fetch shows as a provider status line and the rest of History still renders
