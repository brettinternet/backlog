BL-99's live probe found that archiving or trashing a Linear issue bumps
neither its own updatedAt nor any related issue's, and restoring it
(issueUnarchive) doesn't either. The change window's
filter:{updatedAt:{gte:$since}} therefore never matches on an archive, trash,
or restore alone. BL-92's internal/source/linear/linear.go `Load` re-reads the
issues a trashed row blocks (`row.Trashed && !reconcile`, commit 635774b), but
that row only enters the window's `rows` map if it independently satisfies the
updatedAt filter for an unrelated reason in the same minute (for example, it
was edited and then trashed). The mechanism BL-92 and docs/linear.md describe
("the minute change window sees the blocker as trashed") does not hold as
written; the live fix is coincidental, not deliberate.

BL-99 also confirmed live (/tmp/bl99-probe/or_filter_check.py) that widening
the incremental query's filter to
filter:{or:[{updatedAt:{gte:$since}},{archivedAt:{gte:$since}}]} makes a
freshly trashed or archived issue appear in the window within a minute, at no
extra request cost (complexity is charged by page size, not result count).
This would make BL-92's trashed-blocker re-read actually reachable from the
change window instead of only by chance.

There is no equivalent fix for the restore direction: issueUnarchive clears
archivedAt back to null, leaving no timestamp to filter on, so a restored
blocker's dependents still only recover at the next hourly reconciliation
(bounded by bl next --claim's fresh per-candidate read in the meantime).

Scope: widen linear.go's incrementalQuery filter to the archivedAt OR form,
verify live that it doesn't change empty-window or normal-edit behavior, fix
TestTrashedBlockerRereadsBlockedIssue's fixture so it no longer fakes an
updatedAt bump on the trashed row (it currently sets updatedAt on TEST-1 when
f.trashed, which doesn't reflect live behavior), and correct any remaining
stale claims in docs/linear.md and BL-92's own notes.

## Summary
