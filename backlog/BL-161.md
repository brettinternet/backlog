An agent can store a tour but can't see it afterwards: bl show and bl changes don't mention tours. Add a read path so an agent can confirm what it stored and whether it's stale, and so automation can skip changes that already have one.

## Acceptance criteria

- [x] bl tour ID with no FILE prints the stored tour for each linked change, with its ref and whether it's stale; --json prints the stored tour JSON plus change, ref, and stale
  Evidence: Real run on BL-161: 'bl tour BL-161' printed 'branch:bl-161-read-tour  at 04600ca  3 steps  stale' plus title and numbered steps; --json returns data.tours[] each with item, change, stored, tour, ref, stale. Parity test TestEventsMatchCLI asserts ref and stale:false after storing.
- [x] bl changes ID --json reports per change whether a tour exists for its head (tour: {ref, steps, stale}) without reading it on the TUI update loop
  Evidence: 'bl changes BL-161 --json' showed tour {ref:04600ca…, steps:3, stale:true} after the head moved to b143e42. Loaded in engine.ItemChanges, which is only called from CLI/MCP/StoreTour/history, never the TUI. Parity test asserts the tour field.
- [x] The MCP tour tool reads when no tour is given, matching the CLI's JSON
  Evidence: MCP tour without file calls engine.ReadTours; TestEventsMatchCLI compares MCP and CLI tour read data with reflect.DeepEqual: PASS.
- [x] An item with no stored tour reads as empty, not an error
  Evidence: 'bl tour BL-162' printed 'No stored tours.' with exit 0; --json returned {"tours":[]}. Parity test asserts "tours":[] before storing.
- [x] docs/cli.md, docs/mcp.md, and bl instructions tours describe reading
  Evidence: Updated docs/cli.md (bl tour ID [FILE], changes tour field), docs/mcp.md (tour without file), internal/instructions/tours.md (reading section), and the design.md D43 register.
