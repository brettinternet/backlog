## Why

With several agents working, the first question on coming back is what happened: what finished, what started, what's stuck, which handoffs to read. The event log has every answer, with each write's session, agent kind, and branch (D40), but `bl events --since` takes only an event ID, so you read raw events or ask an agent to.

## Sketch

- `bl events --since` also accepts a duration (`12h`) or a timestamp.
- `bl recap [--since DUR] [QUERY]` groups the window's events by item: created, status moves (`todo → active → done`), criteria progress, comments, the first line of each handoff, and claims gained or lost, each with its agent kind. JSON for agents, and MCP `recap` mirrors it.
- The TUI marks rows updated since its previous session closed (UI state already persists per project), and a filter key toggles to only those.

## Open questions

1. Is a native summary worth it over `bl events --json` plus an agent? The standup skill already combines backlog and GitHub activity.
2. Should merges in the window (first-parent log, already cached) appear, or does recap stay with the event log?
3. The TUI marker needs per-project last-seen state. The query language stays clock- and state-free (docs/query.md), so it would be a TUI toggle, not an `is:` term.

## Recommendation

Below the line. Promote `--since DURATION` on its own first if reading the event log by time keeps coming up: it's small and adds no new shapes.
