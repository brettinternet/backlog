## Why

BL-103 and its children made the change view work: Overview, Files, Diff, Commits, Conversation, review drafts, and tours. BL-166 made an unlinked pull request an item of its own. But the view still can't answer the question you open a PR to ask: **can this land, and if not, what's left?**

Today:

- Merge state isn't read, so conflicts, a branch behind its base, and branch protection are invisible.
- Checks are a flat list with no exact state or duration, and failing checks aren't sorted first. Why a job failed means `O`, then the browser.
- An approval on an old commit looks current.
- Review threads never appear in the Diff. Conversation bodies are plain wrapped text with no code context.
- `enter` does nothing on a check, a file, a reviewer, or a thread.
- A `github-pulls` item opens to near-empty item tabs; its PR is two keys away.
- A thread can't be resolved without the browser.
- Agents still need `gh` and raw GraphQL for why CI failed and which threads are open.

Goal: one place to judge, navigate, and finish a pull request, whether it belongs to a task or is its own unit of work (a D44 `github-pulls` item). Every problem shows on the first screen, and getting to it is one `enter` away.

## Scope rule

The view answers two questions: **can this land**, and **what's left to do** (failing checks, requested changes, unresolved threads). bl models those concepts, which every forge has, and nothing else.

Forge-specific features stay out: merge queues, auto-merge, merge method, per-check required flags, code owners and teams, viewed files, review requests, and suggestion blocks. They remain one `O` (browser) or `!` (`gh` action) away. A new forge field joins only when it changes one of the two answers. This keeps bl from chasing every GitHub feature and keeps the read small enough to maintain.

## Principles

1. **Verdict first.** Every change view tab starts with one line that answers "can this land?" The Overview lists each reason as an entry.
2. **Every entry goes somewhere.** `enter` on a merge reason, check, reviewer, file, or thread opens where it's fixed or explained. `backspace` returns to the exact entry.
3. **Problems first, the rest folded.** Failing then running checks, then unresolved threads. Passing checks and resolved threads fold into one summary entry that `enter` expands.
4. **The forge decides, bl displays.** Merge state and review decision come from the forge; bl never computes mergeability. Stale never reads ready or passing (D43).
5. **Read on demand, bounded.** The list refresh reads only what the list shows. PR detail is read for the change shown. Steps, annotations, and the log excerpt are read for the check shown. Everything runs on workers (D14), is redacted and stripped (D21), and is cached by head or check run.
6. **Same data for agents.** `bl changes ID --detail` and MCP `changes` `detail: true` return what the view shows.

## Layout

Mockups are at 76 content columns, the change view at 80 columns. Glyphs follow the existing set (`✓` passing, `✕` failing, `●` running); final glyphs are verified in a PTY under default, `NO_COLOR`, and high contrast.

### Verdict strip (every change view tab, under the tabs)

```
⇡ #45 → main   ✕ Blocked  1 failing · changes requested · 3 unresolved   12s
```

| Verdict | When (forge merge state first) | Color |
| --- | --- | --- |
| `Ready` | `CLEAN` or `HAS_HOOKS` | green |
| `Unstable` | `UNSTABLE`: mergeable, optional checks failing | yellow |
| `Running` | Only pending checks stand between it and ready | yellow |
| `Blocked` | `BLOCKED`, with reasons: failing or pending checks, changes requested, review required | red |
| `Behind` | `BEHIND`: base requires an up-to-date branch | yellow |
| `Conflicts` | `DIRTY` | red |
| `Draft`, `Merged`, `Closed` | PR state | muted, magenta, muted |
| `Checking` | `UNKNOWN` while the forge computes it | muted |

Reasons are ordered by what to fix first and truncate with `…`. The verdict and the age of the last read never truncate; the age becomes `stale` when a read fails. A stale read never shows `Ready`. Branch and worktree changes show stage, branch, `↑2 ↓1`, and dirty count instead.

### Overview

```
 Merge    ✕ Blocked
   ✕ test (ubuntu-latest) failed
   ✎ ann requested changes                                             2h
   ● 3 unresolved threads
   ⚠ Conflicts with main

 Checks   ✕ 1  ● 2  ✓ 15  – 3
   ✕ test (ubuntu-latest)   failed     4m12s
   ● lint                   running    1m03s…
   ○ deploy-preview         waiting
   ✓ 15 passing · – 3 skipped                                          ▸

 Reviews  ✎ changes requested
   ann          ✎ changes requested   2h
   bob          ✓ approved            1d   outdated
   carol        ○ requested

 About    feat/bl-12-login → main · 3 commits · 12 files +120 −30
          opened 2d by brett · updated 12m · head 3f2a1c9 · closes #33 · BL-12

 (description, Markdown)
```

- **Merge** lists one entry per reason. `enter` on a failing or pending check opens the check, on a review opens that review in Conversation, on unresolved threads opens the Diff at the first one, and on conflicts, behind, or Ready opens `!` narrowed to the change's actions, so merging is `enter` then a pick.
- **Checks** order: failing, then running, queued, or waiting, then passing, then skipped. With more than six checks, passing and skipped fold into one summary entry; `enter` or `za` toggles it. Each row shows glyph, name, exact state word (`queued`, `running`, `waiting`, `failed`, `timed out`, `cancelled`, `action required`, `passed`, `skipped`, `neutral`, `stale`), and duration (elapsed with `…` while running). Duration drops first as width shrinks. `enter` opens the check, `O` its URL.
- **Reviews** lists requested and submitted reviewers with state and age, and `outdated` when the review's commit isn't the head. `enter` opens the reviewer's latest review in Conversation.
- **About** compresses the facts the old property sheet listed. It needs no new reads.
- The existing Draft block stays between Reviews and About.

### Check (`enter` on a check, one level under Overview)

```
 ✕ test (ubuntu-latest)                         failed · 4m12s · 14m ago

 Steps
   ✓ Set up job                                                        2s
   ✓ Run actions/setup-go@v5                                          14s
   ✕ Run go test ./...                                             3m51s

 Annotations
   ✕ internal/auth/login_test.go:42  expected 200, got 500

 Log
   --- FAIL: TestLoginRetry (0.42s)
       login_test.go:42: expected 200, got 500
   FAIL  github.com/acme/app/internal/auth  0.512s
   ##[error]Process completed with exit code 1.
```

- Steps and annotations come from one read. `O` opens the check, step, or annotation.
- **Log excerpt.** For a completed GitHub Actions job (needs Actions read, BL-179): the 100 lines up to and including the first `##[error]` line, or the last 100 lines when there is none. Timestamps are removed, and error and warning lines are colored. `yl` copies the excerpt for pasting into an agent; `O` opens the full log. Without the permission, or while the job runs, the Log line says why and `O` opens the job.
- Other check runs show their output title and summary as Markdown. Commit statuses show their description.

### Conversation

```
 ● internal/auth/login.go:42                            unresolved · 2
   │   if err != nil {
   │ -   return retry(ctx)
   │ +   return retry(ctx, 3)
   ann  2h
     Why 3? Make this a named constant.
   brett  1h
     Done in 3f2a1c9.

 ✎ ann requested changes  2h
     A couple of nits, and the retry needs a test.

 ✓ 4 resolved threads                                                  ▸
```

Order: unresolved threads in file and line order, then reviews and comments oldest first, then resolved threads folded into one entry. A thread shows the last four lines of its diff hunk. Bodies render as Markdown with the description's renderer, on the worker, cached. `enter` on a thread opens the Diff at its line; an outdated thread says its line changed and stays put.

### Diff

```
  41  41    if err != nil {
  42      -   return retry(ctx)
      42  +   return retry(ctx, 3)
          ┃ ● ann 2h  Why 3? Make this a named constant.
          ┃   brett 1h  Done in 3f2a1c9.
  43  43    }
```

Threads render under their line on their side. Unresolved threads are expanded; resolved threads fold to one line (`✓ ann: Why 3? …  2`), and `enter` or `za` toggles them. Drafted line comments show the same way, marked `draft`. `]u`/`[u` move to the next or previous unresolved thread across files.

### Files

Each row shows its unresolved thread count. `enter` opens the Diff at the file. The Conversation tab count shows unresolved threads.

### List and navigation

- The `changes` cell keeps its width, but its last glyph becomes the verdict, by precedence: `⚠` conflicts, `✕` failing, `✎` changes requested, `↓` behind, `●` running, `○` review required, `✓` ready. Drafts and an unknown merge state keep today's checks glyph. This needs `mergeStateStatus` on the list read.
- `gp` from the list or detail opens the item's furthest open pull request in the change view, or its Changes tab when it has several.
- Detail on a `github-pulls` item opens in its pull request's change view. `backspace` shows the item tabs, such as History.
- With a change view open, `J`/`K` keep the same change view tab on the next item's furthest pull request, so you can triage a list of PRs without leaving the view. An item without one shows its item tabs.
- Go-to (`ctrl-p`) accepts `#45` or a pull request URL and selects the item that shows that PR.
- Query: `merge:ready|unstable|blocked|behind|conflicts`, evaluated from the list read, beside the existing `checks:` and `review:`.

### Keys (new or newly meaningful)

| Key | Where | Does |
| --- | --- | --- |
| `gp` | List, detail | Open the item's pull request |
| `enter` | Merge reason, check, reviewer, file, thread | Open its target |
| `enter`, `za` | Folded summary, resolved inline thread | Expand or fold |
| `]u` / `[u` | Change view | Next or previous unresolved thread |
| `x` | Thread (Conversation, Diff) | Resolve or unresolve |
| `yl` | Check | Copy the log excerpt |

Every new action is in the keymap table, help, palette, and which-key popups, and is disabled with its reason where it doesn't apply. Mouse selects entries as today; clicking a selected entry does what `enter` does.

## Freshness

No new cadence. While a change view or the Changes tab shows an open pull request, its detail is read again on each per-minute forge refresh, and `R` reads it at once. When a change action returns, the shown pull request is read again immediately, so a merge shows as Merged. When a shown check finishes or the verdict changes between reads, the status bar says so (`✕ test (ubuntu-latest) failed`, `#45 ready`) until the next key. Nothing reads a pull request that isn't shown.

## Writes

D43 has review writes. This epic adds one: **resolve or unresolve a thread** (`x`), with `resolveReviewThread` and `unresolveReviewThread`. `gh` has no command for it, and it's how addressing feedback ends. It's one mutation on the worker through the account queue, never retried, then reconciled by a re-read. A refused write keeps the forge's reason visible (D15), and it's gated by D10 like `c` and `r`.

Everything else is an action handoff, per the D43 non-goal. Actions suspend the TUI like `$EDITOR`, so `gh`'s own prompts and credentials apply. Shipped examples:

| Action | Command |
| --- | --- |
| Merge | `gh pr merge {change.number}` |
| Update branch | `gh pr update-branch {change.number}` |
| Ready for review | `gh pr ready {change.number}` |
| Convert to draft | `gh pr ready --undo {change.number}` |
| Re-run failed jobs (check view) | `gh run rerun {check.run} --failed` |

`{check.run}` and `{check.url}` are new placeholders, available while a check is shown. `github-pulls` items stay read-only as items (D44).

## Agents

`bl changes ID --detail [--json]` and MCP `changes` with `detail: true` add, for each open pull request:

- `merge`: `state`, `verdict`, `reasons`
- `checkRuns`: `status`, `startedAt`, `completedAt`
- for the first five failing runs: `steps`, `annotations`, and `log` (the excerpt) or `logUnavailable` with the reason
- `reviewers`: `login`, `state`, `submittedAt`, `outdated`
- `threads`: `id`, `path`, `line`, `resolved`, `outdated`, `hunk`, and `comments` (`author`, `body`, `time`, `url`)

Default `bl changes` stays as cheap as today. `bl instructions workflow` names `bl changes ID --detail --json` for "why did CI fail" and "what did reviewers ask" in place of `gh`.

Verify `mergeStateStatus` on the live API first, including whether it still needs a preview header. Without it, the verdict comes from `mergeable` plus the check and review data.

## Safety and budgets

- Logs: credentials never go to the redirect host. The fetch streams, holds at most 100 lines of up to 2 KiB each, stops at the first error line, and aborts past 32 MiB with `O` offered. D21 redaction and control-sequence stripping run before display or cache. The excerpt is cached by check run and attempt in the state directory.
- §11: held `j` over an Overview of 300 checks, a Conversation of 200 threads, and a 10,000-line Diff with 100 inline threads meets the navigation budget. Every read and render runs on workers (D14).
- Request volume: at most one detail read a minute for the shown pull request, plus one check read and one log fetch when a check view opens.

## Register

Record **D45, Pull request view**, in BL-176, and extend it in each later child. The change view answers whether a pull request can land and what's left, from the forge's merge state. It models only concepts every forge has: merge readiness and reasons, checks with exact state and duration, reviews with outdated marks, and review threads, shown inline in the Diff. Merge queues, auto-merge, merge method, required flags, code owners, viewed files, review requests, and suggestions stay behind `O` or `!`. A shown check's steps, annotations, and log excerpt are read on demand, bounded and redacted, never on refresh. The only new write is resolving a review thread, one non-retried mutation reconciled by a re-read. Merging, branch updates, draft state, re-runs, and closing are action handoffs (the D43 non-goal).
