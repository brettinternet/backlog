Follow-up to BL-88, which added the Sprint model for Linear cycles and Jira sprints and named GitHub Projects v2 iteration fields as out of scope. An iteration has an ID, title, startDate and duration; ProjectV2IterationField.configuration lists `iterations` (current and upcoming) and `completedIterations`, but nothing marks one as active. Deriving `current` needs the clock (startDate <= today < startDate + duration, allowing for breaks), which D31 currently forbids. Decide that first: classify states when the catalog is fetched (query evaluation stays clock-free), and record it in D31. Then add the iteration value to the project items query (one more fieldValueByName alias; GitHub already enumerates fully each load) so sprint:, ready.sprint and group:sprint work for GitHub project sources. No catalog I/O on the update loop (D14).

## Acceptance criteria

- [ ] GitHub project sources with an iteration field publish a sprint catalog and per-item sprint; sprint:current|next|<name>, ready.sprint and group:sprint work as for Linear and Jira
- [ ] The iteration field is discovered from the project fields, not hardcoded; projects without one are not sprint-capable
- [ ] Iteration states are classified when the catalog is fetched, never during query evaluation; httptest fakes cover current, upcoming, completed and a break between iterations
- [ ] design.md D31, github.md and query.md document iteration support
