Read the parent epic's Writes section first. Addressing feedback ends with resolving the thread, and `gh` has no command for it, so this is the one native write the view adds. Merging, branch updates, draft state, and re-runs are action handoffs (BL-176, BL-178).

## Scope

- `x` on a thread in Conversation or the Diff resolves or unresolves it with `resolveReviewThread` or `unresolveReviewThread`.
- The write is one mutation on the worker through the account queue and is never retried. The thread shows a pending mark until a re-read confirms the result. After an unknown outcome, the re-read decides what shows; the mutation is idempotent, so this is safe. A refusal stays visible with the forge's reason (D15).
- Gate with D10 exactly like `c` and `r`. Without a write-capable account, or without Pull requests: write on `bl-cli`, `x` is disabled with the reason. GitLab forges don't implement it.
- Extend D45 with the write.

## Tests

- Fake-server tests in `internal/source/github`: the mutation input, no retry after dispatch, and an unknown outcome reconciled by the re-read. These catch a double toggle that would undo the user's action.
- D10 gating reasons, extending `TestOAuthInstallationPermissionGatedWrites`.
- TUI routing of `x` by tab and entry.

## Acceptance criteria

- [ ] x resolves or unresolves the thread under the cursor in Conversation and the Diff, showing pending until a re-read confirms
- [ ] Fake-server tests prove the write is one mutation that is never retried, an unknown outcome is reconciled by the re-read, and a refusal stays visible with the forge's reason
- [ ] Without a write-capable account or permission, x is disabled with the reason, extending TestOAuthInstallationPermissionGatedWrites
- [ ] D45 records the write and docs/tui.md documents x
