## What

The §8 actions: `name`, `run`, optional `cwd` and `key`, `when`, `confirm`, and `detach`. They run from:

- the `!` menu and each action's own key in the TUI
- `bl action NAME ID`
- the MCP `action` tool

Actions share the BL-30 executor: placeholders, value checks, result capture, environment, and depth. Every run ends in an `action.finished` event with outcome and result, so hooks can chain after an action exactly as after a hook. A non-detached action suspends the TUI the way `$EDITOR` does. A detached action returns at once. An action whose placeholders cannot expand for the item (for example `{resource}` without coordination) is shown as disabled with the reason.

Document examples: create a worktree with `wt switch --create {branch}`, start an agent with `worklease run --resource {resource}`, open a Herdr workspace.

## Acceptance criteria

- [ ] Actions appear only for items that match `when`, `confirm` prompts, and keys that conflict with the keymap are reported
- [ ] A PTY test shows a non-detached action suspending and resuming the TUI cleanly; a detached action returns at once
- [ ] The TUI, `bl action`, and MCP `action` run the same executor with identical environment and stdin, and each run appends one `action.finished` event that a hook can chain on
- [ ] An action whose placeholders cannot expand is shown as disabled with the reason and never runs
- [ ] The example actions in docs/automation.md run against fakes in a test

## Plan

1. Reuse BL-30's executor, trust, event context, placeholders/cwd, bounded results and causal depth; add when/capability filtering, confirmation and binding-conflict validation for CLI, TUI and MCP. Define the action-invocation stdin event context consistently in docs/automation.md without adding an undocumented persisted event type.
2. Wire the action menu/palette/custom keys and reuse BL-21 terminal suspension for attached actions; detached actions use the same runner. Missing resource/result values disable an action with a reason. Noninteractive confirmation must fail closed rather than hang.
3. Emit one action.finished for each run, carrying outcome/result so ordinary after hooks can chain. Keep Worklease/worktree/agent knowledge out of core execution; those are configured examples, not built-in workflows.
4. Verify identical invocation stdin/env through all three entry points, PTY suspend/resume, detached completion, disabled placeholders and action.finished -> hook chaining. Run all docs/automation.md examples against fake executables, including the design's work action and agent hook; run task test and task race.
