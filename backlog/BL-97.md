Follow-up to BL-88. The first time a TUI session uses a sprint term, Store.UseSprints starts a refresh, but the sprint catalog is still empty. Until it arrives, sprint:<name> shows "unknown sprint value" and sprint:current matches nothing, with no sign that loading is under way (internal/tui/model.go requestProjection, internal/engine/store.go UseSprints). The filter-bar path also has no test. Keep D14: no I/O on the update loop.

## Acceptance criteria

- [x] While sprint demand is enabled but no capable source has published a catalog, sprint value warnings are suppressed and the view shows the source as loading
  Evidence: mise exec go -- go test ./internal/tui -run TestQuerySprintCatalogLoading: PASS. sprint:Seven typed via filter bar before the catalog loads gives no warning and a syncing badge (no ✓ linear). Removing the eval.go SprintsLoading skip makes it fail with 'unknown sprint value "Seven"'.
- [x] Once the catalog arrives, the projection re-runs and sprint:current shows matching items without further input
  Evidence: mise exec go -- go test ./internal/tui -run TestQuerySprintCatalogLoading: PASS. After the fake store releases the sprint-enabled load, only snapshot messages are pumped (no keys) and sprint:current shows LIN-1; badge returns to synced.

  Evidence: TestQuerySprintCatalogLoading (internal/tui/query_test.go) drives sprint terms through the filter bar against engine.OpenStore with a fake linear-kind source, covering pending (no warning, loading badge, 0 rows) and loaded (match appears, sprint:Eight warns). Verifier PASS.
