## Why

An item shows its current state but not how it got there. Jira has a History tab and Linear an Activity timeline. A `bl` item can't show who changed it, which agent sessions worked it (often several: one or more for implementation, then others for the PR and review phases), what each session concluded, or a way to get back into a session. Today the only trace is `bl show`'s claim history (design.md §9 "Claim history"): a session string and the login user, for example `71e98dd4-… brett`. Nothing records that it was a Claude Code session, which host or checkout it ran in, or how to resume it.

Reopening a recent agent session from the item is the most useful part. The work history matters for days or weeks while the item is in development and review, then gradually stops mattering.

## Principles (decided with the owner, 2026-10-29)

- **Local and decaying, not permanent.** Session records and handoffs live in local state (D22): the project event log in XDG state, never item files or the disposable cache. Remote backlogs get them locally too. Nothing here is required for correctness. Agent transcripts expire (Claude Code's `cleanupPeriodDays`, 30 by default), worktrees get removed, and hosts differ. That's acceptable.
- **Resilient to that decay.** Every history source is independent and optional. A missing or failed source shows one status line and never hides the others. A session row outlives its transcript and checkout: it keeps who, when, the phase, and the handoff text, and loses only the resume affordance, with the reason shown (`checkout removed`, `other host`, `live`, `no agent config`).
- **No imposed Git workflow.** Commit trailers are optional project config, not a convention `bl` assumes.
- **`bl` is not an agent runtime (§2).** It records which agent, renders history, and runs a user-configured resume command. It never stores or reads transcripts.
- **Publishing is opt-in.** Handoffs stay local unless config says to post them as comments.

## Shape

1. **Session identity on events.** Every event a `bl` write or claim produces under a caller session carries a `session` object: `{id, agent, agentSession, host, cwd, branch}`. `agent` is a kind such as `claude`, `pi`, or `codex`, detected from an `agents:` config map (built-in defaults, overridable in user config). The item's sessions are a fold over its events, joined with Worklease claim history by session ID.
2. **Handoffs.** `bl handoff ID TEXT|- --session S` records a short "what I did, what I tried, where I stopped" as a `session.handoff` event. `bl instructions workflow` asks agents for one at done, release, and the end of any unclaimed phase (PR follow-up, review). Optionally `history.handoff: comment` also posts it to the item's source as a comment.
3. **Resume and fork.** User config maps each agent kind to resume and fork argv, such as `[claude, --resume, "{agentSession}"]`, or a Herdr pane split in the current tab. The TUI runs it from a session row in History or from the `!` menu. The CLI runs it with `bl resume ID`.
4. **History tab.** One time-ordered timeline per item: local events (field changes, status, readiness, hooks/actions, claims, handoffs), Worklease claim history, comments, the Git history of the item's file for native and Backlog.md sources, and later provider activity and BL-103's changes. Also available as `bl history ID [--json]` and over MCP, so an agent picking up an item can read previous sessions' handoffs.
5. **Provider activity.** GitHub issue timeline, Linear issue history, and Jira changelog, loaded lazily and read-only.

## Relation to BL-103

BL-103's changes (worktree, branch, PR, landed commit) belong in this timeline as rows: PR opened, checks failed, merged. The Changes tab can stay as the place to drill into diffs. When either ships second, it adds its rows to or reads from the other's model, and it doesn't duplicate the History view. BL-103's commit-trailer decision should read the optional `history.commitTrailer` key defined here.

## Out of scope

- Storing, copying, indexing, or summarizing transcripts.
- Permanent archival, or syncing history across hosts. A remote Worklease authority's claim history shows other hosts' sessions without agent details. That's expected.
- Token, cost, or duration accounting per session. Each harness reports it differently.
- Event-log retention or pruning. Rotated logs are kept indefinitely today (events.md). Revisit only if size becomes a measured problem.
