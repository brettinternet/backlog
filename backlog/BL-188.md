## Why

The mouse already selects, opens, folds, sorts, resizes the split, swipes board columns, and selects text (docs/tui.md Mouse), but a board card can't be dragged, which is the first thing people try on a board.

## Scope

- Pressing on a card and moving at least one cell starts a drag. The target column's header highlights and an insertion marker shows where the card would land.
- Releasing over another column moves the card to that column's status, resolved and refused exactly as `<` and `>` are (D35, D36). A column the item's source can't take names the source in the status bar and writes nothing. A marked card drags all marks, like a bulk status edit, which can't activate marked items (docs/tui.md Coordination).
- Releasing at a position, in the card's own column or another, places it by rank as BL-185's move keys do, where the board's sort allows moves; elsewhere the drop changes only status.
- `esc` cancels a drag. Dropping on a header, outside the board, or back on its own slot does nothing. Dragging past a board edge scrolls columns, as text selection scrolls detail.
- Hit-testing and drawing stay O(viewport) on the update loop, and writes go through the existing edit path (D14, D15).

## Tests

- Model tests with synthetic mouse messages: a drop on another column issues the same mutation as `>`; a drop on a column the source refuses writes nothing and names the source; `esc` cancels. Catches a drag path that bypasses per-source status resolution.
