## Why

Some pull requests have no backlog item. Someone opens a PR for a quick fix, an agent opens one outside the claim loop, or a teammate contributes from a fork. That PR's conversation is the work item: it has a description, reviewers, checks, and a back-and-forth. Today `bl` shows such a PR only as a linked change, and only when an item links to it, so an unlinked PR is invisible in the backlog.

An optional, read-only `github-pulls` source turns each open PR that no item links to into an item. It is separate from the `github` (Issues) source. A PR that any task, issue, or ticket already links to never shows twice.

## Direction (settled; record as design.md D44 in BL-167)

- **Derived from the forge, not a new fetcher.** D43's forge refresh already lists every open PR into a redacted `.pulls.json` (`internal/changes/pulls.go` `RefreshPulls`, `internal/source/github/pulls.go` `Forge`). The source reads through the same forge, cache path, and request queue.
- **Dedup is the linker's existing answer.** A PR is hidden when `changes.Link` links it to any non-`github-pulls` item in the same project, by branch, title, closes, provider closing reference, or refs URL; an ambiguous (`unknown`) link also counts as linked. This needs only the PR list and items, not Git, so it is cheap and runs on a worker (D14).
- **Open and draft PRs only.** Merged and closed PRs leave the source the way finished work leaves a list. The forge always reads every open PR, so the open set is a complete enumeration.
- **Statuses never ready.** `pr-draft` has category backlog and `pr-open` has category active, both fixed by the adapter like D32. Neither is ready, so `bl next` is unaffected. Users fold them into columns with `includes` (D36).
- **Read-only in v1.** Status, comment, and edit writes on GitHub are outward-facing. They're out of scope.
- **Adoption is the exit.** Creating an item whose `refs` include the PR URL links the PR, so the PR item disappears. BL-168 adds a one-step adopt.

## Out of scope (not filed)

These are deliberately left out so v1 stays small. File them separately if wanted.

- GitLab merge requests as items. The data model is already neutral (`changes.PullRequest`), but a `gitlab-mrs` type is separate work.
- Unlinked local worktrees and branches as items.
- Making PRs ready when checks fail or changes are requested.
- PR writes.

- [ ] The diff stays within the task's modified-file list, or Implementation Notes justify the deviation
- [ ] No test was deleted, skipped, or weakened
- [ ] User-visible behavior changes are reflected in README.md or docs/ in the same change
