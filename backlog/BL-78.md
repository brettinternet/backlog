Hooks never retry (D27), which is the right default. After a failure, BL-75's `message` on `hook.finished` says why, but the only way to run the hook again is to cause its event again. A no-op write (`bl set ID status=SAME`) appends an `item.updated` with no changes (internal/engine/events.go:233), which re-fires every matching `item.updated` hook without a `changed:` filter, not just the failed one. Hooks on `item.created`, claims, readiness changes, or another hook's outcome can't be re-fired without a real change. A manual, explicit re-run fills that gap without automatic retries.

Sketch: `bl hooks rerun EVENT_ID NAME [--dry-run]` runs trusted `after` hook NAME against the stored event EVENT_ID as if it were just appended, and appends a new `hook.finished` with `cause` = EVENT_ID and the same depth the original run had. `--dry-run` prints the expanded argv and the hooks that would chain on its outcome, without running anything. It sits beside the hidden detached runner `bl hooks run EVENT_ID...` (internal/cli/hooks.go) and reuses `hooks.RunEvents` with one hook selected, rather than adding a `bl hook` command next to `bl hooks`.

## Decisions

1. **Dedupe.** `hook.finished` versions are `(event ID, hook name, hook digest)` (internal/hooks/runner.go:207), so a re-run with an unchanged hook would collapse into the original. Append `"rerun"` and a random nonce, as no-op writes already do.
2. **Eligibility.** Only `after` hooks. Refuse when the hook is untrusted, its `on` or `if` no longer matches the stored event (evaluate `if` against the event's recorded `item`), the depth cap applies, or the newest `hook.finished` for that event and hook is `ok`, so a successful non-idempotent hook never runs twice by accident. A `refused` run can be re-run once the cause is fixed, for example after `bl trust`.
3. **Chains.** A re-run's `hook.finished` triggers chained hooks like any other. Re-running is an explicit act, as causing the event again is, and `--dry-run` shows the chain first, so a non-idempotent chain such as `worklease run` is the operator's call.
4. **Register.** Amend D27: nothing retries automatically; `bl hooks rerun` re-runs one failed `after` hook by hand.
5. **TUI.** History already shows `hook.finished` rows (`NAME failed`). `!` on a failed hook row offers `Re-run`, as it offers Resume and Fork on a session row. MCP waits until an agent needs it; agents can run the CLI.

## Recommendation

Below the line. BL-75 made failures readable, and the no-op write covers the common `item.updated` case. Promote when a failed hook on another event type costs a fake edit.

## Acceptance criteria

- [ ] bl hooks rerun EVENT_ID NAME runs a failed, timed-out, or refused after hook once and appends a new hook.finished with cause EVENT_ID and the original run's depth; a rerun after an ok outcome is refused

- [ ] Rerun refuses an untrusted hook, a before hook, a hook whose on or if no longer matches the stored event, and a run past the depth cap, each with a reason and without running

- [ ] A rerun's hook.finished triggers hooks chained on it, and --dry-run lists the argv and those chained hooks without running anything

- [ ] In the TUI History tab, ! on a failed hook row offers Re-run, disabled with its reason when refused

- [ ] design.md D27, docs/automation.md, docs/cli.md, and docs/tui.md describe manual re-runs
