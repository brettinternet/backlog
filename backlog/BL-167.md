Add a read-only `github-pulls` source. Every open or draft pull request in one repository that no other item in the project links to becomes an item. Read the parent epic first: its Direction section is settled design. Record that design as design.md D44 in this task's commit.

## Configuration

```yaml
sources:
  - id: prs
    type: github-pulls
    repo: acme/app        # required
    host: github.com      # optional, default github.com
    account: personal     # optional; resolves like a changes forge (engine.forgeAccount)
```

- Reuse the existing `SourceConfig` fields; no new fields. `repo` is required.
- A project-declared source needs `bl trust`, like every remote source.
- Fields that don't apply are refused at config load, naming the field, as for other source types: `path`, `prefix`, `githubProject`, `statusLabels`, `statuses`, `allowWrites`, `jql`, and the rest.
- Update the config JSON schema under `docs/schemas`.

## Items

| Field | Value |
| --- | --- |
| ID | `#N` (source-qualified `prs:#N`). Issue and PR numbers share one namespace per repository, so `#N` never collides with an Issues source on the same repo. A `#N` ID has no letter, so the title link rule can't make a PR link to itself. |
| Title, description | PR title and body, already redacted by `RefreshPulls`. Strip terminal sequences on display, as other provider text is (D21). |
| Status | `pr-draft` (backlog) when `isDraft`, else `pr-open` (active). Fixed by the adapter. A `statuses:` entry giving either key another category fails config load, mirroring D32 (`internal/project/config.go`, around the existing GitHub key checks). Folding them into a column with `includes` works (D36). |
| Assignees | The PR author's login. D42 makes assignees the accountable owner, which for a PR is its author, so `assignee:me` works. Add `author{login __typename}` to `pullsQuery` and an `Author` field to `changes.PullRequest`. |
| Refs | The PR URL. The existing `ref` link rule then shows the PR as the item's own linked change. That gives the change view, checks, and review, and lets `checks:` / `review:` query terms work on PR items for free. |
| Created, updated | The PR's timestamps. |

PRs authored by a GitHub `Bot` (dependabot, renovate, and other GitHub Apps) are skipped. That avoids the most common noise without new config.

Capabilities: read only. Every write (`set`, `note`, `comment`, `ac`, `edit`, `start`, `done`, `archive`) is refused through the existing deny-by-default `model.Capabilities`. Claims are coordination, not writes. `bl claim` and `bl release` work, with the resource key derived as for a GitHub item (`github:` host/owner/repo `#N`; see `internal/worklease/key.go` `resource`). Add the `github-pulls` case there.

## Loading

- Construct the backend in `internal/engine/read.go`'s source factory, beside `github`. Wrap it with `remote.New`, as the GitHub, Linear, and Jira sources are wrapped, so the CLI gets the same warm cache and sync cadence.
- `Load` gets PRs through the same forge (`github.NewForge`, cache path from `newForge` in `internal/engine/changes.go`). The TUI's changes tracker and this source then share one `.pulls.json` and cursor, with no second per-minute fetch of the same repository. Either share one `Forge` per (host, repo, account) in the process, or show in a test that two instances can't corrupt or regress the cache. Its `mu` is per instance today.
- Return `Complete` coverage of open PRs. Merged and closed PRs are omitted, so they leave the source on the next load.
- A forge refresh failure keeps the cached list and marks its rows stale (`Delta.Stale`), never empty.

## Dedup (the core of this task)

After all sources load, the engine hides each `github-pulls` item that `changes.Link` links to any item from another source in the same project. Build it from `changes.Data{PullRequests: ...}` with no Git read. Only rules that apply to a PR's own data matter here: branch (head name), title, closes, provider, and ref. An `unknown` link (an ID naming several items) counts as linked.

- Scope it per project, like `engine.LinkChanges`. In a workspace (D30), a PR linked from another member project does not hide this project's PR item.
- Links to other `github-pulls` items never hide (for example, stacked PRs whose bodies say `Refs #45`).
- It runs on the source/projection worker, never the Bubble Tea update loop (D14). Its cost is O(PRs + items). It applies in every surface: `bl ls`, `bl next`, `bl show`, the TUI, MCP `query`/`show`, and workspaces.
- When an item gains a link (for example `bl set BL-12 refs+=URL`), the PR item disappears on the next snapshot, without waiting for a forge refresh.
- Find where merged snapshots are assembled (`internal/engine/projection.go` and `LoadReads` in `internal/engine/read.go`) and apply the filter at one point that every surface shares. Don't add per-surface filters.

## Identity flip

A PR item can vanish while someone holds its claim, once someone links the PR to a real item.

- `bl show prs:#45` (and MCP `show`) for a hidden PR fails `not-found`, naming the linking item or items. For example: `prs:#45 is linked to tasks:BL-12`.
- `bl release prs:#45 --session S` still releases a held claim on a hidden PR item. Without this, a session holding it would be stuck, because claimed selection refuses fresh selection while a held item is missing. Confirm against the `next --claim` recovery path in `internal/cli` and the engine.
