### Why

Every TUI shares one `tui` session (D39), and a Worklease session holds one claim, so a person can't claim a second item: `claim-held: session already holds …`. People multitask; agents run one loop per session.

### Shape

- Without an explicit session, the TUI coordinates each item under its own session, `tui:<source>:<ID>`. The name derives from the item, so reopening anywhere resumes every claim and replays a pending acquire.
- An explicit `--session`, `BL_SESSION`, or `WORKLEASE_SESSION_ID` keeps one session for everything, as before.
- An item's claim is `mine` when its session is that item's session. Agents keep their own sessions and still see your claims as others'.
- `S`/`D`, status transitions, and renewal use the item's session. The TUI renews every claim it holds, off the update loop, at half the earliest remaining lease.
- D39, docs/tui.md, and docs/cli.md describe it.

## Acceptance criteria

- [ ] Without an explicit session, the TUI claims two items at once, each under tui:<source>:<ID>, and both show mine
- [ ] Reopening the TUI shows both claims as mine and D releases each one
- [ ] An explicit session still coordinates every item under that one session
- [ ] The TUI renews every held claim off the update loop and stops renewing a claim once it is released or lapses
- [ ] D39, docs/tui.md, and docs/cli.md describe per-item sessions
