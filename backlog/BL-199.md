The request scheduler (internal/source/remote/scheduler.go) treats a 429, or a 403 that says "rate limit", without Retry-After or a reset header as limited for 1 s. GitHub's secondary rate limit, which meters concurrent use and server time rather than points, often answers that way. GitHub says to wait at least a minute in that case, and longer each time it repeats. Large repositories' forge refreshes are the reads most likely to hit it.

Outcome: a limited response with no usable Retry-After or reset header refuses that account's requests for 60 s. Each further limited response without one, before a request succeeds, doubles the wait, up to 16 minutes. Any non-limited response resets it. A Retry-After or reset header is still honored exactly, as now. This applies to every provider using the scheduler.

Non-goals: per-forge budgets (the backfill task stops on low remaining quota), retrying writes.

Modified files: internal/source/remote/scheduler.go, internal/source/remote/scheduler_test.go, docs/remote.md.
